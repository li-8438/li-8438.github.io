"这个 RAG 系统好不好用？"

如果回答是"我试了几个问题，感觉还行"，那这个系统迟早会出问题。感觉会骗人，尤其是当知识库从 100 篇文档涨到 1000 篇、当分块参数被人随手改了一次、当换了个 embedding 模型之后。

**没有评测的 RAG 系统，质量只会静默劣化。**

## 一、核心原则：检索和生成分开评

RAG 有两个独立的失败来源：

- **检索失败**：正确的文档没被召回，或者召回了大量噪声
- **生成失败**：文档是对的，但模型没按文档说、或者推理跑偏

这两类问题的**解法完全不同**：前者要调分块、检索策略、embedding 模型；后者要调提示词、上下文构建、或者换更强的模型。

如果只评最终答案质量，你会看到"答案不好"，但不知道该改哪里。所以必须**分开度量**。

## 二、检索侧指标

### Recall@K：召回率

**定义**：在 top-K 条检索结果里，包含正确答案的 query 占比。

```python
def recall_at_k(results: list[list[str]], ground_truth: list[str], k: int) -> float:
    """results[i] 是第 i 个查询的检索结果列表（按相关性排序）。"""
    hits = sum(1 for res, truth in zip(results, ground_truth) if truth in res[:k])
    return hits / len(results) if results else 0.0
```

**它回答的问题**：正确答案有没有被捞出来。

**为什么最重要**：Recall@K 是检索质量的天花板指标。如果正确答案不在 top-K 里，后面 rerank 再强、提示词再好都没用——[Rerank 不能救召回](article.html?slug=rag-rerank)。

生产环境的常见阈值：**Recall@K ≥ 0.9**（门禁默认值通常设在 0.8，但成熟系统会往 0.9 以上推）。

### MRR：平均倒数排名

**定义**：正确答案出现在第几位，取倒数后求平均。

```python
def mrr(results: list[list[str]], ground_truth: list[str]) -> float:
    total = 0.0
    for res, truth in zip(results, ground_truth):
        for rank, doc_id in enumerate(res, start=1):
            if doc_id == truth:
                total += 1.0 / rank
                break
    return total / len(results) if results else 0.0
```

**它回答的问题**：正确答案**排得多靠前**。

- 排第 1 位：得分 1.0
- 排第 2 位：得分 0.5
- 排第 3 位：得分 0.33
- 没召回：得分 0

**为什么重要**：因为上下文条数有限（通常 3-5 条），排在第 10 位的正确答案等于没用。MRR 比 Recall@K 更贴近实际可用性。

常见阈值：**MRR ≥ 0.6**。

### 其他值得关注的指标

| 指标 | 说明 | 用途 |
| --- | --- | --- |
| NDCG@K | 考虑排序位置的加权得分，比 MRR 更平滑 | 综合排序质量 |
| 关键词覆盖率 | 答案里是否包含了 ground truth 的关键词 | 生成侧的内容完整性 |
| 场景隔离率 | 问题属于场景 A，检索结果是否只来自 A | 多场景数据隔离是否生效 |
| 模板命中率 | 是否命中了预期的 Prompt 档位 | Prompt 路由是否正确 |
| 表格行召回率 | 表格类问题是否召回正确的行 | 表格处理的专项回归 |

最后三项是**业务定制指标**，它们往往比通用指标更能反映真实问题。比如"场景隔离率"低，说明数据隔离的过滤条件没生效——这是安全问题，比召回率低几个点严重得多。

## 三、生成侧指标

检索对了，生成还可能出错。生成侧主要看三个维度：

**忠实度（Faithfulness）**：答案里的每一条陈述，是否都能在检索到的上下文中找到支撑。

计算方式通常是用一个模型把答案拆成若干 claim，逐个验证是否被上下文支持：

```
忠实度 = 被上下文支持的 claim 数 / 总 claim 数
```

**这是防幻觉的核心指标**。高风险的金融、医疗、法律场景，通常要求忠实度 > 0.85。

**答案相关性（Answer Relevance）**：答案有没有真正回应问题。检索到了正确文档，模型也忠实于文档，但答非所问——这种情况并不少见。

**上下文精度（Context Precision）**：检索到的上下文里，有用内容的占比。噪声越多，这个值越低，同时模型的注意力被稀释，生成质量也会下降。

RAGAS、DeepEval 这类工具可以自动算这些分数。但要注意：**它们是补充分析手段，不能替代工程回归门禁**——因为它们依赖 LLM 打分，本身有波动，不适合做 CI 里的硬性卡点。

## 四、评测集怎么建

### 规模

**100 条左右**是一个好的起点。太少没有统计意义，太多维护成本高。

### 内容必须来自真实

这是最容易做错的一点。评测集如果全是自己编的"完美问题"，测出来的分数会虚高，线上真实问题照样崩。

正确的来源：

- 线上用户的真实提问日志（最有价值）
- 客服/业务人员整理的高频问题
- 已知的 bad case

### 每条要标什么

```json
{
  "query": "差旅住宿费的标准是多少",
  "scenario_id": "enterprise_knowledge",
  "expected_source": "hr_data",
  "expected_doc_id": "travel_policy_v3",
  "expected_keywords": ["住宿费", "上限", "城市级别"],
  "intent": "KNOWLEDGE_QUERY",
  "risk_category": "pricing"
}
```

关键是要有 **expected_doc_id**（用于算 Recall@K 和 MRR）和 **expected_keywords**（用于算关键词覆盖率）。

### 分层

评测集要按类型分层，这样出问题时能快速定位：

| 子集 | 用途 |
| --- | --- |
| 主链路回归 | 常规问答 |
| 表格回归 | 表格类问题 |
| 负样本边界 | 越界问题是否被正确拦截 |
| 多轮追问 | 追问改写是否生效 |
| 场景隔离 | 数据隔离是否生效 |
| 性能基线 | 各场景的延迟基线 |

**负样本边界尤其重要**：测的不只是"该答的能不能答对"，还有"不该答的是不是真的拒答了"。很多人只测前者，上线后被用户套出越界回答才后悔。

## 五、质量门禁：把评测接进 CI

评测跑完不能只是"看一眼分数"，要变成**硬性卡点**。

```python
@dataclass
class EvaluationGate:
    min_recall_at_k: float = 0.8              # 召回率下限
    min_mrr: float = 0.6                      # MRR 下限
    max_error_rate: float = 0.0               # 错误率上限（零容忍）
    min_scenario_recall_at_k: float = 0.8     # 单场景召回下限
    min_scenario_mrr: float = 0.6             # 单场景 MRR 下限
    min_source_recall_at_k: float = 0.8       # 单 source 召回下限
```

几点设计经验：

**全局指标 + 分组指标都要有。** 全局 Recall 0.85 看起来还行，但可能是"7 个场景都是 0.95，1 个场景只有 0.3"的平均结果。所以要同时卡**单场景**和**单 source** 的下限。

**错误率零容忍。** 检索报错、超时、返回异常这类问题不该有容忍度——它们通常意味着配置错误而不是质量问题。

**门禁失败要有可读的报告。** 光说"Recall 0.78 < 0.8"没用，要能直接看到**哪几条 query 没召回、召回的是什么**，否则排查成本极高。

## 六、Bad Case 闭环

评测集建好只是开始。真正的价值在于**持续把线上问题沉淀回评测集**。

```text
线上运行
   │
   ├─ 用户反馈 / 低置信答案 / trace 异常
   ▼
Bad Case 收集
   │
   ├─ 人工确认（这一步不能省）
   ▼
进入回归评测集
   │
   ▼
下次改动时自动拦截同类问题
```

### 自动提取

从评测报告里自动提取失败案例：

```bash
python scripts/extract_bad_cases_from_report.py \
    --report reports/evaluation/core_chain_latest.json \
    --output eval_sets/local_bad_cases.json
```

### 人工确认后提升为回归用例

```bash
python scripts/promote_bad_cases_to_regression.py \
    --source eval_sets/local_bad_cases.json \
    --target eval_sets/business_depth_regression.json
```

**"人工确认"这一步不能省。** 自动提取的 bad case 里混着标注错误、预期不合理的情况，直接全量进回归集会污染评测集，反而降低门禁的可信度。

### 闭环的价值

这个闭环一旦转起来，系统的质量就是**单调递增**的——每修一个问题，就永久多一道防线，同类问题不会再出现。

没有这个闭环，同样的 bug 会反复出现：这次改了分块参数导致表格召回变差，三个月后有人又改一次，同样的问题再来一遍。

## 七、可观测性：Trace 是评测的前提

所有评测都依赖一个前提：**出问题时你能看到链路内部发生了什么**。

每次请求至少要记录：

- 各阶段耗时（路由、意图、改写、检索、重排、生成）
- 首 token 延迟
- 检索诊断信息：路由结果、意图、查询变体、top_k、命中分数、Prompt 档位
- 最终使用的来源引用

没有这些，线上出现 bad case 时你只能看到"用户问了 X，系统答了 Y"，完全无法判断是**检索没召回**、**召回了但被上下文构建过滤掉**、还是**模型没按上下文说**——这三种情况的修法完全不同。

LangSmith、Langfuse 这类工具可以做链路追踪。但即使不接外部工具，本地也要把诊断信息落盘。

## 小结

RAG 评测的第一原则是**检索和生成分开评**——它们的失败原因和解法完全不同。

检索侧核心看 **Recall@K**（有没有捞到）和 **MRR**（排得多靠前），前者是天花板，后者贴近实际可用性。生成侧看**忠实度**（是否被上下文支撑）、**答案相关性**、**上下文精度**。

评测集要**100 条左右、来自真实问题、按类型分层**，负样本边界测试不能少。评测要接进 CI 做**质量门禁**，同时卡全局指标和分组指标。

最有价值的是 **Bad Case 闭环**：线上问题 → 人工确认 → 进入回归集 → 永久拦截同类问题。这一步能让系统质量单调递增。

最后，所有这些都依赖 **Trace 可观测性**——看不到链路内部，就无从谈优化。

到这里 RAG 的技术链路就完整了。还有一个工程维度常常决定项目成败：知识库的版本管理和数据隔离，见 [RAG 知识库治理：版本、隔离与入库质量](article.html?slug=rag-knowledge-governance)。
