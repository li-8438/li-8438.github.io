有一个判断 AI 产品强弱的土办法，只需要问三个问题：

**它能做什么动作？它改了什么？怎么回滚？**

再加一个：**谁批的？**

答不上来的，基本都是**贴了新标签的聊天框**。它在 Demo 里可能很惊艳，但一旦进入采购流程就会崩掉——因为采购方问的恰恰就是这四个问题。

## 一、聊天框为什么是最容易做错的第一步

2023 到 2025 年间，"产品里有 AI"通常意味着三种东西之一：对话式搜索、copilot、或者一个助手标签页。这三种都是聊天框的变体。

问题不在于聊天框不好，而在于**它优化错了目标**：

| | 聊天（Chat） | 工作流（Workflow） |
| --- | --- | --- |
| 优化目标 | 惊喜度、参与度 | 完成率、正确性、可追溯 |
| 成功标准 | "回答得挺好" | "这件事办完了，且能证明" |
| 失败形态 | 答非所问 | 改错了东西 |
| 用户心态 | 咨询 | 委托 |

**从咨询到委托，是一整个量级的风险跃迁。** 你可以容忍一个顾问偶尔说错话，但你不能容忍一个被授权操作你数据库的执行者偶尔手滑。

市场条件早就不是障碍了——模型更快更便宜，开源权重模型在窄任务上已经可用。**真正的约束是买家的纪律**：在经历了几年的试点之后，企业要的是证据——周期时间是否下降、队列是否变短、收入流程是否加快。

"我们的模型更聪明"已经打动不了人了。**"这是我们端到端负责的工作流，这是它触碰的范围，这是我们如何保证它安全"才能拿到预算。**

## 二、范式迁移：从"对话即终点"到"对话即起点"

这是我认为今年最本质的变化，用一个例子就能说清。

**过去（对话即终点）**：你对 AI 说"帮我订一张明天北京到上海的机票"。AI 用对话形式给你推荐班次、购票网址、出行提示。**交互到此结束**，剩下的你自己去办。

**现在（对话即启动）**：你说同样的话，AI 查航班、比价、推荐班次、等你选择、出票。**对话只是把意图告诉 AI 的方式，后面一连串动作由 AI 跑完。**

这个迁移的后果比看起来严重得多：

> **对话本身不再是价值的全部，它降级成了一种可落地的需求指令、Agent 服务的基础层。**

由此重构的是企业的生存法则：**价值不再仅由前端交互体验决定，还取决于你是否具备被调度和执行的能力。**

一个佐证：2026 年 5 月全球 AI 应用的 token 消耗排行榜 Top 20 里，Agent 占了 9 个；万亿级 token 消耗的 6 大产品中，**Agent 占了 5 个**。

## 三、App 正在退化成 Agent 的后端

这是上面那条法则的直接推论。

当 Agent 能直接调用航空公司 API 订票时，用户还需要打开订票 App 吗？**App 的角色正在从"用户界面"变成"Agent 的后端服务"。**

Salesforce 推出的 Headless 360 把整个 CRM 平台通过 API 暴露出来，让 Agent 在没有人打开浏览器的情况下操作——这个动作的信号意义很强。

跟上节奏的企业都在做同一件事：**把原有产品功能拆解为可独立调用的模块，不再要求用户打开自己的界面。**

而这会筛出两类活得下来的玩家：

- **平台型**：打通开发者生态与私域数据
- **深耕型**：在垂直领域握有通用 AI 难以覆盖的行业专属流程与核心数据

被挤掉的中间层是：**既没有技术壁垒也没有行业积累的套壳者**，以及**不愿意开放 API、导致 AI 无法读取调用的传统软件**。

## 四、保证不是来自"模型更聪明"，来自设计

这是本篇最想传递的一点。

很多人以为 Agent 能不能上生产，取决于模型够不够可靠。实际上，**保证（guarantees）几乎不来自模型"答对"，而来自系统设计**：

- **类型化的工具**（typed tools）
- **schema 与校验**
- **确定性的检查**（金额对不对、记录存不存在、权限够不够）
- **审计日志**，能事后证明发生了什么
- **审批门禁**，高风险动作必须有人点头

一个很说明问题的行业动向：**用脚本强制关键步骤的顺序，而不是指望模型理解。** Salesforce 的 Agent Script 就是这个思路——银行 Agent 必须在谈论账户余额之前完成身份验证，这个顺序不是靠模型"懂"，是**靠硬编码逻辑强制的**。

听起来像是在给 AI 上枷锁，实际上是**让 AI 变得可用**。一个"通常能做对"的 Agent 在企业里没有位置；一个"保证关键步骤做对"的 Agent 才能上生产。

## 五、隐藏的成本不是 token，是异常

这是最容易被算错的账。

大家盯着 token 花费，但真正吃掉利润的是**异常**：那些奇怪的 case、半对半错的输出、以及**制造返工的静默错误**。

一句很扎心的判断：

> **如果一个 Agent 的失败方式是需要高级员工来清理现场，那你不是自动化了，你是新建了一个 on-call 轮班。**

所以严肃的工作流团队把成功定义成运维指标：

| 指标 | 为什么是它 |
| --- | --- |
| 任务完成率 | 而不是"回答满意度" |
| 升级到人工的比例 | 直接衡量可委托性 |
| 工具调用错误率 | 定位失败发生在哪一层 |
| 平均修复时间 | 衡量可恢复性 |
| 事故频率 | 衡量风险 |

**把它当成一个 SRE 问题来处理**：加监控、设错误预算，**并且把自主程度卡在实际表现之上**——表现不达标就不给更多权限。

## 六、三个活得下来的模式

观察了一批跑通的产品之后，有三个模式反复出现。

**模式一：retrieve-then-act（先取后做）。** 先从受治理的源里取事实，再用允许的工具行动。**不要先生成、再指望检索来"佐证"。** 顺序反了，幻觉就有了着落点。

**模式二：plan with checkpoints（带检查点的规划）。** 把工作拆成若干步，每一步产出**可验证的中间产物**。这样错误会在造成后果之前被拦住，而不是在终点被一次性发现。

**模式三：policy-first UI（策略优先的界面）。** 让用户设定约束——区域、花费上限、数据源、审批规则——然后系统在这些约束内运行。**而不是乞求用户写出完美的提示词。**

第三个模式特别值得注意，它意味着交互的重心从"怎么问"转移到了"定什么规矩"。**这是产品设计的位移，不是 UI 的调整。**

## 七、风险分级：把自主权当成可授予的东西

配套的动作分级几乎是强制项：

| 风险级别 | 例子 | 处理方式 |
| --- | --- | --- |
| 低 | 读数据、搜索 | 自动执行 |
| 中 | 写 staging、创建草稿 | 记录日志，可审查 |
| 高 | 写生产、对外发消息、花钱 | **必须人工审批** |

一条硬规则：**永远不要让 Agent 在没有审批门禁的情况下直接接触生产系统。**

还有一条实现上的细节——**未登记的动作按最高风险处理，而不是最低。** 白名单思维在这里会出事。

## 八、一个正在发生的反向信号

不是所有"更多工具"都带来更好的结果。

Amazon Prime Video 的工程团队在生产里发现，**给 Agent 通过中心化 MCP server 提供全面的工具访问，反而降低了性能**——工具越多越混乱、幻觉越多、结果越差。他们的解法是渐进式工具发现：初始化时只暴露一个"找工具"的能力，按需加载 3-4 个相关工具，把工具上下文从 405000 token 压到 1600-2500。

这个例子很好地说明了本篇的主题：**Agent 产品的竞争力不在"给了 AI 多少能力"，而在"在什么时机给它哪些能力"。** 这是设计，不是集成。

## 九、容易踩的坑

**把聊天框当成最终形态。** 它是最容易做出 Demo 的形态，也是最难形成壁垒的形态——因为通用对话能力正在被大厂快速内化。

**先生成后检索。** 让模型先说话、再找证据，等于邀请它编。顺序必须是先取后做。

**把自主程度当成卖点。** 一线调研反复显示：**最终胜出的可能不是最自主的系统，而是组织信任到敢于规模使用的系统。**

**只算 token 不算异常。** 前者是线性成本、可预测；后者是尾部风险、会吃掉你所有的利润。

**不设错误预算。** 没有"做到什么程度才配拿到更多权限"的门槛，自主权就是一次性赌博。

## 小结

把这一切串起来看，2026 年 AI 产品的竞争优势可以用一句话概括：

> **不是"智能"，而是被包装成软件的可靠性：紧凑的范围、受治理的动作、以及可审计的结果。**

那些活得下来的 Agent 产品，看起来像**可靠的系统**，而不是一个聪明的聊天窗口。

还有一个更远的判断值得记着：**Agent 最重要的发展阶段，可能是用户不再把它当成一个独立品类的那一天。** 就像人们打开流媒体应用时不会想到推荐算法、叫外卖时不会想到路由软件——当 Agent 特性消融在邮箱、银行、购物和工作流软件里，那才是比"再多一个聊天机器人"深刻得多的变化。
