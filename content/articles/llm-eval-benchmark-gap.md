先看两个数字。

**第一个**：截至 2026 年中，主流大模型在 MMLU 上普遍能拿到 88% 以上。

**第二个**：多个企业部署审计交叉验证出的一致结论——**榜单分数与生产实际表现之间存在约 37% 的落差。**

一个更具体的案例：某头部金融客户的意图分类模型，测试集 F1 达到 **92%**，上线后业务实际通过率只有 **68%**。

这不是模型不行，是**我们一直在用错误的东西衡量"行不行"**。

## 一、榜单饱和悖论

先给这个现象一个名字。它的结构是：

```
学术榜单表现            生产现实
92% 准确率      ──▶     68% 执行成功率
```

落差来自三个结构性的原因，每一个都不是"模型再强一点"能解决的。

### 原因一：数据污染

公开榜单是静态的，而训练语料是从网上刮来的。榜单题目和答案不可避免地会渗进预训练语料——不是谁故意作弊，而是在互联网规模的数据上训练时，榜单内容本就公开存在于博客、讲义、讨论里。

**结果是高分可能反映的是模式识别和记忆，而不是泛化推理。** 这也解释了为什么原始分数一路涨，落差却始终消不掉。

### 原因二：格式洁癖 vs 用户混沌

榜单用的是干净、结构化、为考察特定能力而设计的输入。生产环境里的用户输入是：

- 直接粘贴带残缺语法的原始日志
- 省略必要参数
- 一句话里包含互相冲突的指令
- 用方言、拼音、内部缩写提问

有个真实案例里的细节很典型：用户用"固收"指代"固定收益产品"，用粤语拼音混合输入——这些在测试集里一条都没有。

### 原因三：无状态评测 vs 有状态执行

榜单在隔离环境里测模型。而生产里的 Agent 跑的是**多步有状态循环**：查数据库、调外部 API、解析 JSON schema、跨轮次维护会话状态。

关键在这里：**第 2 步的一个小错误，会在 8 步的执行链里被放大成整体失败。**

榜单根本不测这个。

## 二、离线评测看不到 30-40% 的真实失败模式

如果说上面是"榜单不靠谱"，那这一节是更难受的部分：**连你自己建的测试集也不够。**

LangChain 在 2025 年 12 月做的 Agent 工程现状调查（1340 份回复）里有两组数字：

- **52.4%** 的组织在测试集上跑离线评测
- 只有 **37.3%** 跑线上评测
- 而在**已经有 Agent 上生产**的团队里，这个比例升到了 **44.8%**

最后一行说明什么？**这个教训是靠吃过亏学到的，不是靠预判学到的。**

而离线评测漏掉的真实失败模式，量级在 30-40%。

### 分布为什么会漂

三个机制在起作用：

**一、测试集是建造者写的。** 他们知道预期用例，写出来的 prompt 天然贴合自己设计的意图分类。真实用户不知道你的分类体系，他们会用完全不同的说法、组合出你没想到的能力组合、偶尔要求 Agent 做点超出设计范围但相邻的事。

**二、多轮对话里上下文会累积。** 用户在前面几轮已经确立了若干事实，这个上下文形态是单轮测试用例几乎不会复现的。客服和研究分析类 Agent 尤其危险——对话长、用户提供的密集事实多，Agent 必须在不编造的前提下跟踪它们。

**三、工具输出会变。** 你的离线测试集 mock 了外部 API。当真实 API 改了响应 schema 或开始偶发报错时，你的测试集一点都不会红。

## 三、三层评测框架

解法不是"放弃离线评测"，而是**分层**。离线评测仍然有用——它抓回归。但只能把它当下限，不能当上限。

| 层 | 抓什么 | 抓不到什么 |
| --- | --- | --- |
| 离线（curated set） | 部署前的回归 | 生产里的未知未知 |
| 基于 trace | 真实失败回流 | 未被采样的低频问题 |
| 线上（行为信号） | 用户实际感受到的质量 | 单次调用的细粒度对错 |

### 第一层：离线评测

作用：**阻止变坏**。每当你换模型版本、改提示词、重建 embedding 索引，跑一遍。

写进 CI，当成单元测试看待。

### 第二层：基于 trace 的失败回流

这是最容易被跳过、也最值钱的一层。核心机制是：**把生产中的失败自动变成测试用例。**

```python
def capture_failure(trace_log):
    """生产失败自动进入测试集"""
    if trace_log.get("status") == "FAILED" or trace_log.get("human_escalation"):
        return TraceEvaluationCase(
            session_id=trace_log["session_id"],
            raw_user_input=anonymize(trace_log["user_input"]),  # 先脱敏
            expected_tool_call=trace_log["correct_tool"],
            expected_output_schema=trace_log["expected_schema"],
            failure_category=trace_log["error_type"],
        )
    return None
```

两个必须做对的地方：

**一、脱敏。** 生产 trace 进测试集之前必须过一层净化，剥掉 PII / PHI。这既是合规要求，也是让测试集可以长期留存的前提。

**二、用确定性断言，慎用 LLM-as-judge。**

这一点值得强调。LLM-as-judge 很方便，但它引入了新的不确定性——你在用一个会波动的系统去衡量另一个会波动的系统。

**能确定性断言的，就不要用打分**：

- JSON schema 是否严格匹配
- API 参数类型是否合法
- 工具调用序列是否正确
- 引用 ID 是否指向真实的 passage ID
- 该拒答的时候是否拒答、该执行的时候是否执行

主观质量才交给 rubric 或人工，而且要**算评分者间一致性**。

### 第三层：线上行为信号

有些指标只存在于生产流量里，任何离线测试都造不出来。

**重复提问率**是最有说服力的一个：Klarna 的客服 Agent 上线后重复咨询下降了 25%——这个信号说明答案足够好、用户不需要回来再问一次。**它无法在任何离线测试集里被观测到。**

其他值得建的信号：任务完成率、升级到人工的比例、工具调用错误率、平均修复时间、事故频率。

## 四、Golden Set 怎么建

一个有参考价值的做法是把测试集分层，而不是随机采样：

| 层级 | 来源 | 占比 | 更新频率 | 标注要求 |
| --- | --- | --- | --- | --- |
| 核心集 | 人工标注的高价值 query | 15% | 季度 | 三级质检、专家交叉验证 |
| 边缘集 | 日志里的高频长尾 case | 45% | 月度 | 双人标注，Kappa > 0.8 |
| 压力集 | 对抗测试生成的样本 | 20% | 双周 | 规则生成 + 扰动强度检测 |
| 噪声集 | 随机误触发输入 | 20% | 月度 | 自动过滤，监控误报率 |

注意两个设计意图：

**边缘集占最大头（45%）。** 因为生产里出问题的地方就在长尾，不在核心场景。

**噪声集占 20%。** 这是为了测"该拒答的时候会不会拒答"——一个只会答不会拒的系统，在生产里比什么都不做的系统更危险。

冷启动阶段（1-2 周）可以这么起手：

1. 采最近 30 天生产日志
2. 用 K-means 做语义聚类（n_clusters=50 左右）
3. 每类抽 20 条代表性样本
4. 标注

然后把更新机制写进去：

```python
def update_golden_set(logs, current_set):
    new_samples = detect_shift(logs, current_set)
    if len(new_samples) > 100:
        clustered = cluster_samples(new_samples)
        prioritized = sort_by_impact(clustered)   # 按业务影响排序
        return current_set + prioritized[:100]
    return current_set
```

关键是**这个更新必须是自动的**。靠人记得去更新评测集，三个月后一定断更。

## 五、该测什么：从"答案对不对"转向"任务成不成"

生产环境关心的指标和榜单完全不是一回事：

| 维度 | 榜单测的 | 生产该测的 |
| --- | --- | --- |
| 正确性 | 单次回答准确率 | 任务成功率（可 rubric 或 schema 校验） |
| 工具 | 通常不涉及 | 工具调用成功率、参数合法性、输出是否被正确使用 |
| 引用 | 不涉及 | 引用 ID 是否指向真实 passage |
| 拒答 | 不涉及 | 拒答正确性（该拒的拒、该做的做） |
| 延迟 | 通常忽略 | p50 / p95 首 token 与端到端耗时，真实并发下 |
| 恢复 | 不测 | 重试、降级、修复提示、缓存 |

有一条我特别想强调：**拒答正确性需要单独建 ground truth 去测。** "拒答"不是一个标签，是一个需要策略对齐的判断——过度拒答和拒答不足同样致命。

## 六、容易踩的坑

**用公开榜单做模型选型。** 这是最典型的架构反模式：

```python
# 反模式
def select_model_for_production(task_type):
    if task_type == "data_extraction":
        return "model-with-highest-mmlu-score"   # 错得离谱
```

正确的做法是**用你自己的生产 query 分布去测**。

**指标与业务目标错配。** 前面那个金融案例里，原始指标体系测的是准确率 92%、响应时间 350ms、吞吐 100 QPS——全都没错，但业务真正需要的是"拒答是否合理""高峰时段是否稳定""突发流量下怎样"。**测了一堆正确但无关的东西。**

**评测集三个月不更新。** 这是最常见的失效方式，也是最难自我发现的一种——因为分数一直在出，看起来一切正常。

**认为"能验证"是可选的。** 一个很硬的判断标准：**如果你设计不出验证方式，这个任务就不该交给 Agent 自主完成。** 这不是保守，这是工程判断。

**把评测当成一个阶段。** 评测是持续生产评测（CPE）流水线，不是一个上线前的关卡。

## 小结

这篇的结论可以压缩成两句话。

**第一句**：高榜单分数制造的是虚假的安全感。在企业级 AI 生产里，**如果系统遇到真实用户数据就崩，那么静态学术指标毫无意义。**

**第二句，也是更重要的一句**：**评测不是一个技术活，是一个产品决策。**

为什么这么说？因为"什么算成功"这个问题，工程团队答不了。一个答案"基本正确但漏了一个限定条件"算成功还是失败？一个拒答，是谨慎还是无能？这些只能由理解业务的人来定义。

而反过来看，前面提到的"成功那 12%"具备的四个特征里——部署前的基础设施投入、治理文档、基线指标、**明确的业务归属方**——前三个都是评测问题，第四个是评测能落地的前提。

**没有人为 Agent 的行为负责，就没人会认真定义什么叫"做对了"。**
