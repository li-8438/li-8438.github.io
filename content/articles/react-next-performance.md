前端性能优化有个很常见的误区：一提到“优化”，脑子里先跳出来 `useMemo`、`React.memo`、`useCallback`。这些 API 解决的是“避免重复计算”，但绝大多数慢页面慢在别的地方——**发给浏览器的东西太多了**。

一个直观的对比：给一个 200 行的组件加 `memo`，可能省下 2ms；把首屏 JS 从 800KB 砍到 300KB，在中端安卓机上能省下 1 秒以上。前者是常数级收益，后者才是量级差异。

这篇不谈怎么记那些记忆化 API，只谈**优先级**：哪些事收益最大，哪些事做了等于没做。

## 一、先量再改：别用体感做优化

优化的第一步不是改代码，而是确认瓶颈在哪。常见的问题是拿开发机的体感去推断用户——开发机有缓存、CPU 快、网络好，和用户手里的中端安卓机完全是两回事。

**看三个核心指标就够了。**

| 指标 | 衡量什么 | 常见瓶颈 |
| --- | --- | --- |
| LCP | 最大内容渲染，首屏“看起来出来了” | 图片太大、字体阻塞、服务端慢 |
| INP | 交互到下一帧的响应延迟 | 主线程长任务、重渲染范围过大 |
| CLS | 布局偏移量 | 图片没预留尺寸、字体 swap 引发跳动 |

**实验室数据和真实用户数据各有各的用处。** Lighthouse 适合发现明显问题和做回归对比，但它跑在模拟环境里；真正该盯的是真实用户监控里的 P75。一个页面 Lighthouse 95 分、但 P75 的 INP 有 400ms，说明高分是跑分环境给的幻觉。

**给自己定预算。** 比如“首屏 JS 不超过 300KB（gzip 后）”“单张图片不超过 200KB”。有了数字，code review 时才有的可讨论的基础，否则性能问题永远停留在“感觉有点慢”这种无法推进的描述上。

## 二、服务端优先：把工作留在服务端

最大的一笔收益，通常来自**把原本要在浏览器做的事挪到服务端**。

三类渲染方式的选择其实很直接：

- 内容基本不变（博客、文档、营销页）→ 构建期生成静态页，用户拿到的是纯 HTML，JS 只做增强
- 内容因人而异但不必实时（后台报表）→ 服务端渲染 + 缓存
- 强交互（编辑器、画布、实时协作）→ 客户端渲染

很多项目的默认姿势是“全部客户端渲染”，这等于把取数据、拼模板、做格式化全都丢给用户的手机。改成服务端渲染后，用户拿到的是已经拼好的 HTML，JS 只需要接管交互部分。

**数据获取的位置很关键。** 在客户端 `useEffect` 里发请求，会形成“HTML 到了 → JS 下载 → JS 执行 → 才发请求 → 数据回来再渲染”的瀑布，每一环都是串行等待。把请求挪到服务端，这条瀑布直接消失。

## 三、缩小客户端边界

在 Next.js 的 App Router 里，默认所有组件都是服务端组件，只有真正需要浏览器 API 的部分才标 `'use client'`。

**`'use client'` 是有传染性的。** 一旦在某个组件顶部标了它，这个组件**及其整个子树**都会被打包进客户端 bundle。最常见的错误是在页面顶层或布局层随手标一个，结果整棵树都被送到了浏览器。

正确做法是把它推到**叶子节点**：

```jsx
// 页面本身保持服务端组件
export default async function ArticlePage({ params }) {
  const article = await getArticle(params.slug);   // 在服务端取数据
  return (
    <article>
      <h1>{article.title}</h1>
      <ArticleBody content={article.content} />
      {/* 只有这个按钮需要浏览器状态 */}
      <LikeButton slug={params.slug} />
    </article>
  );
}
```

```jsx
// LikeButton.jsx —— 客户端边界收敛在这一小块
'use client';
import { useState } from 'react';

export function LikeButton({ slug }) {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked(!liked)}>
      {liked ? '已点赞' : '点赞'}
    </button>
  );
}
```

**超过首屏的东西按需加载。** 弹窗、图表库、代码高亮、富文本编辑器——这些又大又不是立刻要用的，用动态导入拆出去：

```jsx
import dynamic from 'next/dynamic';

// 用户滚动到或点开时才加载
const HeavyChart = dynamic(() => import('./HeavyChart'), {
  ssr: false,
  loading: () => <div className="chart-skeleton" />,
});
```

## 四、静态资源策略

这一块的收益经常比代码层优化大得多，而且改动小。

**图片通常是最大的一块。** 一张 2MB 的 PNG，换成 WebP/AVIF 并给到实际显示尺寸，可能只剩 40KB。要点：

- 用现代格式（WebP / AVIF），配合 `srcset` 给不同屏幕尺寸
- 明确写 `width` / `height`，否则图片加载完成时页面会跳一下，直接伤 CLS
- 首屏图片别懒加载，首屏之外的才加 `loading="lazy"`

**字体是容易被忽略的阻塞项。** 自定义字体没配好会导致文字区域白屏一段时间。用 `font-display: swap` 让文字先用系统字体显示出来；中文字体务必做子集化——完整字体动辄几 MB，子集化后可能只剩几十 KB。

**缓存头要设对。** 带 hash 的静态资源可以长期缓存：

```
Cache-Control: public, max-age=31536000, immutable
```

HTML 本身则相反，应该 `no-cache`，否则用户会拿到过期的页面结构。

## 五、可感知性能

用户感受到的“快不快”，不完全等于指标数字。

**骨架屏和占位符。** 内容没来之前先占好位置，用户会觉得“在加载了”而不是“卡住了”。注意骨架尺寸要接近真实内容，否则加载完反而跳动。

**乐观更新。** 点赞、收藏这类操作，先更新 UI 再发请求，失败才回滚。网络好的时候用户几乎感知不到延迟。

**别阻塞主线程。** 长任务（大量计算、大列表渲染）会让点击和滚动全部卡住。能挪到 Worker 的挪走，长列表用虚拟滚动，大计算量拆成小片让出主线程。

## 六、容易踩的坑

**顶层 `'use client'` 传染整棵树。** 最典型的性能事故来源。写之前先问一句：这个组件真的需要 `useState` 或浏览器 API 吗？

**把所有状态塞进一个 Context。** Context 变化会让所有消费它的组件重渲染。状态应该按“谁用就放谁附近”来组织，不要图省事全挂到根上。

**过早使用 `useMemo`。** 它本身也有成本（比较依赖 + 存缓存）。对于一次简单的字符串拼接或几个元素的 `map`，直接算往往更快。真正该 memo 的是**大计算量**和**引用稳定性会影响下游**的场景。

**只看构建体积不看运行时。** 打包体积小不代表运行快。一个组件逻辑简单但每次渲染都触发几十个子组件更新，照样卡。

**给 `key` 用数组下标。** 列表插入删除时会导致 React 错误复用组件状态，产生诡异的 UI bug——这首先是正确性问题，其次才是性能问题。

**优化完没有回归基线。** 改完就走，过两周换个依赖体积又涨回去。把体积和关键指标接进 CI，超预算就报警。

## 小结

优先级从上往下排：

1. **先测量**，盯 LCP / INP / CLS 的 P75，定出可讨论的预算
2. **服务端优先**，能静态化就静态化，能服务端取数就别放客户端
3. **把 `'use client'` 推到叶子节点**，别让它传染整棵树
4. **处理图片和字体**，这是改动最小、收益最稳的一块
5. **按需加载**非首屏的重依赖
6. **用骨架屏和乐观更新**改善可感知性能
7. 最后才考虑 `useMemo` 这类微观手段

一个判断标准：**如果你说不清这次优化省了多少毫秒、影响了哪个指标，那大概率是在做无用功。**

把“内容以 Markdown 为唯一来源、页面只负责渲染”这件事做到极致，就是静态站的思路——本站的搭建方式见 [用 GitHub Pages 发布模块化静态博客](article.html?slug=static-site-github-pages)。
