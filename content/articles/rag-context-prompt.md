前面几篇都在讲怎么把正确的文档找出来。但检索到好文档，和生成好答案之间，还隔着一步——**上下文构建**。

这一步常被低估。很多人以为就是把 top-k 的文档拼成一段字符串塞进 prompt，实际上它直接决定答案质量，也是防幻觉的关键位置。

## 一、为什么需要三重约束

检索返回的候选不能直接用作上下文。有三个必须施加的约束：

### 约束一：分数阈值

低于 `min_context_score` 的候选直接丢弃。

这条最容易被忽略，也最危险。假设 top-5 的分数是 `[0.81, 0.45, 0.23, 0.21, 0.19]`，只有第一条真正相关。如果全塞进去，模型会从那四条低分文档里"汲取灵感"，生成混着错误信息的内容。

**宁可上下文少，不要塞噪声。**

### 约束二：条数上限

`final_context_top_n` 限制条数，通常 3-5 条。

上下文不是越多越好。大模型存在 **lost in the middle** 现象——对长上下文**开头和结尾**关注度高，**中间部分**关注度显著下降。塞 20 条进去，模型可能只认真看了前后各两条。

### 约束三：字符数上限

两个层面：

- `max_context_chars`：总字符数上限，控制 prompt 体积和成本
- `max_context_doc_chars`：单条字符数上限，超出截断

第二条尤其重要——防止一篇超长文档独占整个上下文空间，把其他相关来源全挤掉。

```python
def select_context_docs(faq_hits, doc_hits, plan) -> list[Document]:
    """按三重约束筛选上下文。"""
    def append_doc(doc: Document, key: str) -> None:
        # 1. 去重：同一文档只保留最高分
        if key in seen:
            return
        # 2. 分数阈值
        if doc.score < plan.min_context_score:
            return
        content = doc.page_content
        # 3. 单条字符数超限则截断
        if len(content) > plan.max_context_doc_chars:
            content = content[: plan.max_context_doc_chars].rstrip() + "…"
        # 4. 总字符数超限则停止（至少保证有一条）
        if used_chars + len(content) > plan.max_context_chars and selected:
            return
        selected.append(doc)
        used_chars += len(content)
```

## 二、去重与来源排序

### 按文档去重

如果用了[查询变体](article.html?slug=rag-query-optimization)或父子块，同一份内容可能被多次召回：

- 多个变体召回了同一个 chunk
- 同一个父块下的多个子块同时命中

不去重会导致上下文里出现重复内容，浪费宝贵的字符预算，还会让模型误以为"多个来源都这么说"（其实是一个来源）。

去重 key 要用**稳定的 chunk_id**，而不是内容全文——这样父块下的多个子块能被正确识别为同一来源。

### 来源排序：FAQ 优先还是文档优先

默认 FAQ 优先（标准答案可信度更高），但有个例外：

```python
if plan.prefer_table:
    # 表格类问题优先保留表格行上下文
```

当用户问的是表格类问题（比如"某个参数的阈值是多少"），表格行的证据价值高于一般性描述，此时应该让文档（表格行）排在前面。

这种"按问题特征动态调整排序"的细节，是检索质量调优的重要抓手。

## 三、Prompt 档位：两维路由

不同问题需要不同的回答策略。这里用**两个维度**来决定最终的提示词模板。

### 维度一：意图

| 意图 | 档位 | 设计意图 |
| --- | --- | --- |
| `FAQ_QUERY` | `faq_answer` | 短、准、直接复用标准答案 |
| `KNOWLEDGE_QUERY` | `knowledge_answer` | 允许按流程、规则、步骤结构化回答 |
| `FOLLOW_UP` | `follow_up` | 结合历史理解指代，焦点限定在当前问题 |

### 维度二：风险类别

独立于意图的第二维度：

| 风险类别 | 档位 | 特殊要求 |
| --- | --- | --- |
| `pricing` | 费用口径 | 必须区分已确认/未确认信息 |
| `compliance` | 合规风险 | 保守回答，明确标注依据 |
| `troubleshooting` | 排障操作 | 按步骤引导 |
| `summary` | 资料总结 | 结构化归纳 |

### 选择优先级

**风险类别专用 > 意图专属 > 默认兜底。**

这条规则很关键：即使意图识别为普通知识咨询，只要问题被判定为"费用类"，就必须走费用模板。因为**业务口径的安全性优先级高于交互形式的适配性**。

```python
@dataclass(frozen=True)
class PromptProfile:
    """最终回答阶段使用的提示词档位，创建后不可修改。"""
    name: str
    system_template: str
    user_template: str
    reason: str

    def as_dict(self) -> dict[str, str]:
        # 只暴露 name 和 reason，不暴露完整 prompt 文本
        # 原因：避免调试日志中泄漏提示词细节
        return {"name": self.name, "reason": self.reason}
```

两个设计细节：

**frozen=True**：模板创建后不可变。模板变更必须走代码审查，防止运行时被意外篡改导致口径风险。

**as_dict 只暴露名称和原因**：调试信息里不输出完整提示词，避免日志泄漏。

## 四、模板里必须写什么

看一个真实的回答模板：

```
你是{assistant_name}，负责把{business_domain}中的资料解释给用户。

必须遵守：
1. 优先基于给定上下文回答，流程步骤、功能边界、制度要求、技术方案、适用对象只能来自上下文。
2. 可以按"已确认信息、处理步骤/业务说明、注意事项、后续建议"组织答案，
   但不要为了凑结构编造信息。
3. 费用、合同、就业/收益承诺、权限审批等敏感事实只能来自上下文。
4. 上下文不足时，明确说明"信息不足，无法确认"，并引导联系人工支持：{support_contact}。
5. 回答要适合{industry}场景，清楚说明能确认的信息和不能确认的信息。
```

逐条拆解它的设计意图：

**第 1 条：划定知识来源。** "只能来自上下文"——这是 RAG 防幻觉的核心指令。不说这句，模型会自由调用参数化知识。

**第 2 条：允许结构化，但禁止凑结构。** 这一条很精妙。要求模型按结构回答，会诱导它为了填满结构而编造内容。所以必须同时加上"不要为了凑结构编造信息"。

**第 3 条：敏感事实二次强调。** 费用、合同、承诺、审批这类内容错了后果严重，单独列出强化约束。

**第 4 条：给出"不知道"的出口。** 这是整段模板里最重要的一条。

**第 5 条：要求区分能确认与不能确认。** 比笼统的"要准确"具体得多，模型更容易执行。

### 一条铁律：必须允许模型说"不知道"

这一条值得单独强调。

如果你在模板里只说"请基于上下文回答"，而不给"信息不足时怎么办"的出口，模型在遇到上下文缺失时会**硬编一个答案**——因为它的训练目标就是"给出一个回答"。

而一旦明确告诉它"上下文不足就说信息不足"，它才敢说不知道。

**给模型留退路，是防幻觉最有效的一招。**

## 五、上下文为空时必须拒答

光在提示词里说还不够，代码层要硬拦：

```python
if context.hit_type == "insufficient_context":
    answer = build_insufficient_context_answer(context)
    yield from _finish_with_single_answer(context, history, query, answer, ...)
    return None   # 直接返回，不调 LLM
```

**所有候选都低于阈值时，直接返回"信息不足"，绝不调用 LLM。**

为什么要这么硬？因为如果这时候还让模型生成，它一定会基于参数化知识编一个答案。而你将完全无法判断这个答案里哪些来自知识库、哪些来自模型记忆——**RAG 的可溯源性就彻底失效了**。

用户对 RAG 应用的信任建立在"答案有据可查"上。一次编造，信任就没了。

## 六、引用：让答案可溯源

### 要求模型带引用

模板里要求模型在答案中标注引用编号，对应到具体的来源文档。

### 程序化补强

但模型经常漏写引用。所以生成后要做补强：

```python
answer = enforce_answer_citations(raw_answer, answer_prepared.context_docs)
```

检查三件事：

1. 答案里有没有引用编号
2. 编号是否合法（在来源列表范围内）
3. 引用的来源是否真的支撑了答案内容

缺失时在末尾补上"参考来源"。

### 引用补强 ≠ 事实核验

这里有个容易混淆的点，必须拆开：

> 引用补强只是**修补展示文本**，让答案看起来完整可溯源；它**不等于**事实核验。

补上引用编号不代表答案内容正确。所以代码里的顺序是：**先补引用，再做生成后核验**，两件事分开执行、分开记录。

## 七、一个容易踩的坑：上下文顺序

lost in the middle 现象意味着：**把最相关的文档放在开头和结尾，把次要的放中间**。

很多人直接按检索分数降序排列——这会让最相关的在开头，但次相关的紧随其后，最不相关的在结尾。

更好的排列是：

```text
最相关 → 次相关 → ... → 次要 → 第三相关
   ↑ 开头                      ↑ 结尾
```

或者干脆：**只有 3-5 条时，按分数降序即可**（总量小，位置效应不明显）。条数多的时候才需要考虑重排位置。

## 小结

上下文构建是检索和生成之间的关键一环，三重约束缺一不可：**分数阈值**过滤噪声、**条数上限**避免注意力稀释、**字符数上限**控制成本和防止单条独占。

Prompt 档位用**意图 × 风险类别**两维路由，优先级是"风险类别 > 意图 > 默认"——业务口径安全优先于交互形式。

模板设计里最重要的一条是**必须给模型"不知道"的出口**：明确的"上下文不足就说信息不足，并引导人工支持"，比任何"请准确回答"的空话都有效。代码层还要硬拦——候选全部低于阈值时直接拒答，不调 LLM。

最后，引用补强只补展示、不等于事实核验，两者必须分开。

到这里 RAG 的检索和生成链路就完整了。但怎么知道它到底好不好？见 [RAG 评测：从 Recall@K 到 Bad Case 闭环](article.html?slug=rag-evaluation)。
