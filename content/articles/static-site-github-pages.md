决定用静态站，本质上是一次**复杂度搬家**：把“运行时的复杂度”（服务器、数据库、进程、扩缩容）换成了“构建期和客户端的复杂度”。搬得值不值，取决于你的站点属于哪一类。

本站就是这套思路的产物：没有后端、没有数据库、没有构建步骤，文章是 `content/` 下的 Markdown，页面用 `fetch` 把它们读进来在浏览器里渲染。

## 一、什么样的站适合静态化

判断标准只有一条：**内容的变化频率，远低于内容的访问频率。**

适合静态化的典型场景：

- 个人博客、技术笔记、文档站
- 作品集、简历页
- 活动落地页、产品介绍页
- 内部知识库（访问多、更新少）

不适合的场景也很明确：需要用户登录、需要写入、内容实时变化、需要按用户个性化渲染首屏。这些需求不是“静态站做不了”，而是**做起来要引入一堆外部服务，最后复杂度反而比直接起个后端更高**。

## 二、内容与页面分离

这是整套方案的地基：**文章以 Markdown 为唯一来源，页面只负责排版和导航。**

```
content/
├── articles.json     # 文章目录（全站核心索引）
├── site.json         # 首页配置
├── profile.json      # 关于我
└── articles/*.md     # 正文
```

新增一篇文章只需要两步：写一个 md 文件，在 `articles.json` 里登记一条。页面代码一行都不用改。

**索引是唯一入口，这是最容易踩的坑。** 列表、搜索、分类统计、相关文章推荐，全部读 `articles.json`。只传了 md 却忘了登记，文章在站点上等于不存在——而且不报错，就是“悄悄消失”。

反过来，Front Matter 的优先级更高（加载时是 `{...索引条目, ...md 的 Front Matter}`），所以只改 md 不更新索引也能让详情页生效，但**列表页读的是索引**，两边要保持同步才不会出现“详情页改了、列表页还是旧的”。

## 三、两种仓库形态与路径前缀

Pages 有两种仓库形态，访问地址不同，配置也不同。

| 形态 | 仓库名 | 访问地址 | 是否需要路径前缀 |
| --- | --- | --- | --- |
| 用户站 | `用户名.github.io` | `https://用户名.github.io` | 不需要 |
| 项目站 | 任意名字 | `https://用户名.github.io/仓库名/` | **需要** |

项目站的路径前缀是新手最容易卡住的地方。站点根路径变成了 `/仓库名/`，所有静态资源的绝对路径都会 404。解决办法是把前缀集中到一个配置里：

```js
// assets/js/config.js
export const BASE_PATH = "/仓库名";   // 用户站保持 "/"
```

然后所有资源路径都经过它拼接，而不是散落在各处硬编码。**集中一处，改一次就够**——如果每个 HTML 里都写死路径，迟早漏掉一两个。

## 四、本地预览：为什么不能双击 HTML

这是静态站新手的第二个坑：直接双击 `index.html`，页面一片空白。

原因是页面用 `fetch` 读取 `content/`，而 `file://` 协议下浏览器会拦截这个请求（跨域限制）。必须起一个本地静态服务：

```bash
python -m http.server 4173
# 然后打开 http://127.0.0.1:4173
```

**能用 `file://` 打开的静态站和不能打开的，架构上是两种东西。** 前者要求所有内容内联进 HTML，后者才支持“内容与页面分离”。选了后者，就接受必须起服务这个约束。

## 五、主动放弃的能力与替代方案

静态站没有后端，有些能力是**必须主动放弃**的。诚实地列出这些，比硬撑着用奇怪的方案模拟更有价值。

| 能力 | 静态站能做吗 | 替代方案 |
| --- | --- | --- |
| 阅读量统计 | 做不了真实的 | 直接不做，或接第三方计数 |
| 评论 | 需要外部服务 | 接 giscus / utterances（用 issue 当评论库） |
| 点赞 | 只能本地 | localStorage 存本地状态，换个浏览器就没了 |
| 搜索 | 可以做 | 拉取索引后在客户端过滤，数据量小时完全够用 |
| 在线编辑 / CMS | 做不了 | 改 Markdown 后 git push |
| 服务端渲染 | 做不了 | 用客户端渲染，或改用构建期生成 |

**关键是要诚实。** 一个用 localStorage 做的点赞按钮，换个浏览器数据就没了——那就明确告诉读者这是本地的情绪开关，而不是假装它是真实统计。假装的统计比没有统计更有害。

## 六、成本与配额边界

Pages 对个人仓库免费，但有配额：

- 仓库建议控制在 1GB 以内
- 带宽软限制约 100GB/月
- 构建频率约每小时 10 次

对个人博客来说这些数字非常宽裕——除非你把大量图片或模型文件塞进仓库。**图片该走图床或 CDN，仓库只放文本。** 如果文章里图片很多，仓库体积和流量会成为真正的瓶颈。

另外，Pages 只服务静态文件，不要指望在上面跑任何服务端逻辑。需要服务端能力时，正确的做法是把那部分拆成独立服务（比如云函数），而不是想办法在 Pages 里绕。

## 七、什么时候不该用 Pages

- 需要用户登录、权限、写入操作
- 内容需要实时更新（行情、监控面板）
- 依赖服务端渲染做 SEO 且页面数量巨大
- 需要自定义域名证书之外的服务端配置
- 团队里有人需要不通过 git 就能发文

最后一条尤其重要：**写作者是否接受 git 工作流，决定了静态站能不能长期活下去。** 如果内容由非技术同事维护，要求他们学会 git push 是不现实的，这时候 CMS + 后端反而更简单。

## 八、容易踩的坑

**加了 md 忘了登记索引。** 文件传上去了，站点上找不到，还不报错。

**日期写成 `2024-5-8`。** 排序用的是字符串比较，`2024-5-8` 会排到 `2024-12-01` 之后（字典序里 `5` > `1`）。必须补零写成 `2024-05-08`。

**分类名和分类树不一致。** 文章不会出现在对应分类里，同样是静默消失。分类是靠**中文名**匹配的，改了树里的名字，老文章就从这个分类里消失了。

**缓存住了旧的 `articles.json`。** 明明发了新文章却看不到。请求要带 `cache: "no-store"`，强制每次问服务器。

**JSON 里写注释。** JSON 标准不允许注释，写了 `//` 会让 `JSON.parse` 直接抛错、整页白屏。字段说明要单独写在 md 文档里。

## 小结

静态站的核心取舍：

1. **适合“更新少、阅读多”的内容**，不适合写入型和实时型
2. **内容与页面分离**，索引是唯一入口，别忘了登记
3. **项目站要配路径前缀**，集中到一处配置
4. **必须起本地服务预览**，`file://` 下 fetch 会被拦截
5. **主动放弃真实统计和评论**，用客户端搜索、本地点赞、复制链接替代，并且诚实标注
6. **图片别塞仓库**，仓库只放文本

想清楚这些边界，静态站能省掉一整套运维。前端侧的性能收益也是同一套思路的延续，见 [React 性能优化之路](article.html?slug=react-next-performance)。
