前面几篇讲的都是"检索和生成"的算法问题。但真正决定 RAG 项目能不能长期活下去的，往往是另一类看起来不性感的工程问题：

- 知识库更新了一批文档，怎么保证效果不会变差？
- 变差的能不能一键回滚？
- A 部门的人能不能检索到 B 部门的机密文档？
- 上传了一份全是乱码的扫描件，系统能发现吗？

这些都属于**知识库治理**。它不提升单次检索的准确率，但决定了系统能不能被信任。

## 一、版本管理

### 为什么需要版本

知识库不是静态的。企业文档每周都在更新：制度改了、产品迭代了、旧资料废止了。

如果直接覆盖更新，会面临三个问题：

1. **更新后效果变差了，回不去。** 旧数据已经被覆盖
2. **无法验证新版本好不好。** 新旧版本没法对比，只能"上线后看用户反应"
3. **追溯困难。** 三个月前的某条回答是基于哪版资料生成的？不知道

### 三个版本号

一个成熟的知识库版本体系要管理**三个独立的版本维度**，因为它们的变更原因和影响完全不同：

| 版本 | 变了说明什么 | 变更频率 |
| --- | --- | --- |
| `kb_version` | 知识内容本身更新了 | 高（每周/每月） |
| `embedding_model_version` | 换了 embedding 模型 | 低（半年/年） |
| `chunk_schema_version` | 改了分块策略或元数据结构 | 低 |

**为什么必须分开？**

换 embedding 模型时，知识内容没变，但所有向量必须重算。如果只用一个 kb_version，你无法区分"这次重建是因为内容更新"还是"因为换了模型"——而这两者的回滚策略完全不同。

### 稳定 chunk id 要纳入版本维度

这一点是版本管理的基石。chunk id 用**内容稳定哈希**生成，且必须包含版本维度：

```python
def chunk_identity(page_content: str, metadata: dict) -> tuple[str, str]:
    """基于正文和标准元数据生成 parent_id 与 chunk_id。"""
    parent_id = stable_hash(
        metadata.get("scenario_id"),
        metadata.get("kb_version"),                  # 知识版本
        metadata.get("embedding_model_version"),     # 模型版本
        metadata.get("chunk_schema_version"),        # 切分 schema 版本
        metadata.get("doc_id"),
        parent_content,
    )
    chunk_id = stable_hash(parent_id, page_content)
    return parent_id, chunk_id
```

这样做带来三个能力：

**增量重建**：内容没变的文档，哈希不变，不需要重新向量化。1000 篇文档改了 10 篇，只需要处理 10 篇。

**版本隔离**：不同版本的 chunk 天然不会混在一起。

**变更检测**：对比两版 id 集合，立刻知道哪些文档新增、哪些删除、哪些修改。

### 版本切换流程

```text
当前 active = v2
    │
    ├─ 1. 新版本入库：构建 v3（不影响线上）
    │
    ├─ 2. 评测：对 v3 跑回归评测集
    │
    ├─ 3. 版本对比：v2 vs v3 的召回对比报告
    │       └─ 发现 v3 在某场景召回退化 → 停在这里，不激活
    │
    ├─ 4. 激活：active = v3（原子切换）
    │
    └─ 5. 观察：出问题则回滚 active = v2
```

关键设计：**新版本入库不影响线上**。v3 构建期间，线上仍然检索 v2。只有激活动作是原子的、瞬时的。

**版本对比**这一步最容易被跳过，但它价值最大——在激活之前就能发现"新版本在 A 场景变好了，但在 B 场景退化"，避免带着问题上线。

## 二、数据隔离

### 为什么必须在检索层做

企业 RAG 系统几乎必然面临多租户、多部门、多密级的场景。

一个常见的错误做法是：把所有文档都检索出来，然后指望模型"不要说不该说的"。

**这是行不通的。** 提示词是软约束，模型可能被诱导输出——这就是为什么[提示词不能作为唯一安全防线](article.html?slug=prompt-security-defense)。

正确做法是**检索层硬过滤**：不符合权限的文档，根本不出现在候选集里。模型没见过的数据，再怎么注入也套不出来。

### 四个隔离维度

| 维度 | 含义 |
| --- | --- |
| `tenant_id` | 租户（不同公司/客户） |
| `dataset_id` | 数据集（同一租户内的不同数据集合） |
| `visibility` | 可见级别（公开/内部/机密） |
| `allowed_roles` | 允许访问的角色列表 |

这些字段写入每个 chunk 的 metadata，检索时作为过滤表达式：

```python
results = client.hybrid_search(
    collection_name="kb_docs",
    reqs=[dense_req, sparse_req],
    ranker={"strategy": "rrf"},
    limit=20,
    filter='tenant_id == "t01" and dataset_id in ["d1","d2"] '
           'and visibility != "confidential" and kb_version == "v3"',
)
```

### 三个实践要点

**过滤条件要在检索阶段注入，而不是检索后过滤。** 检索后过滤会导致"本该返回 20 条，过滤完只剩 3 条"——召回率被悄悄吃掉，而且你完全不知道。

**隔离维度要纳入评测。** 前面提到的**场景隔离率**指标就是干这个的：问题属于场景 A，检索结果是否 100% 来自 A。这个指标不达标意味着数据泄漏风险。

**默认拒绝优于默认允许。** 权限字段缺失时，应该视为"不可访问"而不是"可访问"。

## 三、入库质量检查

"垃圾进，垃圾出"在 RAG 里体现得淋漓尽致。文档入库是最后一道能在离线阶段发现问题的关口——一旦脏数据进入向量库，线上检索出问题再排查，成本要高一两个数量级。

### 该检查什么

**低质量 chunk 检测**

- 长度异常：过短（< 20 字符，可能是切分残留）或过长（接近上限，可能没切开）
- 内容异常：纯数字、纯符号、重复字符、无意义的页眉页脚
- 编码异常：乱码、连续的替换字符

**文档级风险统计**

- 表格/OCR 风险：表格行是否为空、OCR 结果置信度是否过低
- 空文档或近空文档
- 重复文档（相同或高度相似的文档多次入库）

**FAQ 与正文冲突检测**

这一项最容易被忽略，但很重要：如果 FAQ 里写"报销时限是 30 天"，而正文文档写"报销时限是 60 天"，用户问到这个问题时，系统可能给出任何一个答案——**两个来源互相矛盾，模型无法判断**。

这类冲突必须在入库阶段检测出来，交给业务人员确认。

### 质量报告与门禁

```python
def check_ingestion_quality(report) -> list[str]:
    """入库质量门禁：返回问题列表，非空则阻断激活。"""
    problems = []
    if report.empty_chunk_ratio > 0.05:
        problems.append(f"空 chunk 占比过高：{report.empty_chunk_ratio:.1%}")
    if report.conflict_count > 0:
        problems.append(f"检测到 {report.conflict_count} 处 FAQ/正文冲突，需人工确认")
    if report.low_quality_ratio > 0.1:
        problems.append(f"低质量 chunk 占比过高：{report.low_quality_ratio:.1%}")
    return problems
```

原则：**质量报告是给人看的，门禁是给 CI 用的**。报告要详细到能定位具体是哪个文件的哪个块有问题；门禁只卡关键红线。

### 风险项不一定要阻断

注意区分两类问题：

- **必须阻断**：编码乱码、空文档、FAQ/正文冲突——这些会直接导致错误答案
- **仅告警**：文档偏长、图片较多、OCR 置信度略低——这些只影响部分场景

一刀切地阻断所有风险项，会让入库流程变得极其难用，最后被人绕过。**门禁太严等于没有门禁**。

## 四、多格式文档的治理

企业资料格式很杂：Markdown、PDF、Word、PPT、Excel、扫描件。每种都有特定的坑。

**表格**：不能按文本切，要[行级语义化](article.html?slug=rag-chunking-strategies)，保留表头、sheet 名、行号。

**扫描件 PDF**：没有文本层，直接解析出来是空的。需要走 OCR 流程，而且**OCR 结果必须人工复核**才能进入正式资料目录——OCR 识别错误的数字进了知识库，会变成错误答案的来源。

一个稳妥的流程是：

```text
扫描件 PDF
   │
   ├─ PaddleOCR + PyMuPDF → 生成"待复核" Markdown + OCR 报告
   │
   ├─ 人工复核（这一步不能省）
   │
   └─ 复核通过 → 提升脚本 → 进入正式资料目录 → 版本重建
```

**Markdown**：先按标题结构化切分，再递归切分。标题层级本身就是最好的语义边界。

## 五、治理能力的优先级

如果资源有限，按这个顺序建：

1. **数据隔离**（安全第一，出事就是事故）
2. **入库质量检查**（防止脏数据进库，投入产出比最高）
3. **版本管理**（支持回滚，是"敢改"的前提）
4. **版本对比与评测**（持续优化的闭环）

数据隔离排第一，因为它涉及的是**安全性**而不是质量——一次数据泄漏的代价，远超检索准确率低几个百分点。

## 小结

知识库治理不提升单次检索准确率，但决定系统能不能被信任、能不能长期维护。

**版本管理**的核心是管三个独立版本号（知识内容、embedding 模型、chunk schema），用**纳入版本维度的稳定 chunk id** 支撑增量重建和快速回滚。新版本入库不影响线上，激活前必须做版本对比。

**数据隔离**必须在**检索层硬过滤**——模型拿不到的数据才安全。隔离维度要纳入评测（场景隔离率），权限缺失时默认拒绝。

**入库质量检查**要拦三类问题：低质量 chunk、文档级风险、FAQ 与正文冲突。门禁卡关键红线即可，太严会被绕过。

最后，多格式文档各有各的坑：表格行级处理、扫描件必须走 OCR + 人工复核、Markdown 按标题结构化切分。

到这里，整个 RAG 系列从链路、检索、生成到治理就完整了。回头看，真正决定 RAG 系统能不能上生产的，往往不是某个算法技巧，而是这些"什么时候不检索""检索结果能不能用""出问题怎么回滚"的工程决策——完整链路见 [RAG 核心链路：从提问到带引用的答案](article.html?slug=rag-core-pipeline)。
