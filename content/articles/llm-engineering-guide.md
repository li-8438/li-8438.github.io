大模型接入业务系统，难点通常不在第一次 API 调用——那往往半小时就能跑通。**难点在于它是一个会波动、会限流、会变贵、还会悄悄变笨的外部依赖。**

很多团队的 Demo 很惊艳，上线后却问题不断：偶发超时、输出格式时好时坏、账单涨得比流量快、换了模型版本之后效果说不清变好还是变坏。这些都不是模型能力问题，是工程问题。

核心心态转变是：**把大模型当成一个不稳定的外部依赖来设计，而不是当成一个函数调用。**

## 一、先想清楚边界

在动手之前，先明确三件事，能省掉后面大量返工。

**第一，这个环节允许多高的错误率。** 摘要写差一点用户可能不在乎；自动退款审批错一次就是事故。错误容忍度决定了要不要人工复核、要不要降级、要不要多模型交叉验证。

**第二，延迟预算是多少。** 同步对话场景可能只能给 2 秒，离线批处理可以给 10 分钟。预算决定了能不能用长思考链、能不能做多轮自检。

**第三，一次调用花多少钱是可以接受的。** 把单次成本乘以日活和人均调用次数，算出来的数字经常让人重新设计流程——比如加缓存、比如用小模型做初筛。

## 二、整体架构：把模型封装成服务

**永远不要让业务代码直接调用某家模型厂商的 SDK。** 把模型能力收进一个独立服务层，业务只依赖你自己的稳定接口：

```python
class LLMService:
    """业务层唯一依赖的模型门面。换厂商/换模型/加缓存，都只改这里。"""

    async def summarize(self, markdown: str) -> str: ...
    async def classify(self, text: str, labels: list[str]) -> str: ...
    async def extract(self, text: str, schema: type) -> dict: ...
```

这一层承担的事情比想象中多：

- **供应商抽象**：用 OpenAI 兼容接口统一 `base_url / api_key / model`，换厂商只改配置
- **重试与超时**：放在这里，不要让每个调用方各写一遍
- **缓存**：同内容同任务直接复用结果
- **降级**：主模型不可用时切备选，或返回兜底文案
- **埋点**：延迟、Token、成功率、失败原因，统一在这里上报

一条稳妥的链路是：**数据层负责采集与清洗，模型层负责调用与评估，服务层提供 API 与告警，应用层对接业务系统。** 每层之间用显式的数据结构交接，不要靠“传一段字符串”贯穿全流程。

## 三、模型选型：按你的任务分布评估

**不要只看榜单分数。** 通用榜单和你手上的任务分布往往不是一回事。

正确的做法是：先冻结一批**代表真实分布的评测样本**（几十到几百条就够），然后拿候选模型跑一遍，看的是四个维度的组合：

| 维度 | 为什么看它 | 典型权衡 |
| --- | --- | --- |
| 质量 | 任务准确率、格式稳定性 | 大模型通常更好 |
| 延迟 | 首 token、整体耗时 | 大模型更慢 |
| 成本 | 每千次调用的 Token 花费 | 可能差一个数量级 |
| 稳定性 | 输出格式是否始终合规 | 小模型容易跑格式 |

**结论往往是分层的**：用大模型处理难的、低频的、高价值的请求，用小模型处理简单高频的。比如意图识别用小模型，复杂推理和生成用大模型。

**保留切换能力本身就是价值。** 模型迭代极快，半年内换两三次是常态。把 `base_url / api_key / model` 做成配置而不是硬编码，切换成本才会低。

## 四、数据与评测集：先冻结，再迭代

**高质量、能代表真实分布的评测集，比堆模型重要得多。**

流程上建议：

1. 从真实请求里采样，构造初始评测集（覆盖典型场景 + 边界情况）
2. **冻结它**，之后所有提示词改动、模型更换都跑这个集
3. 每次改动记录分数，形成可对比的回归基线

**对用户输入做前置处理，能显著降低线上抖动：**

- **长度截断**：超长输入直接截断或分段，避免偶发的超限失败和成本尖峰
- **脱敏**：手机号、身份证、密钥在进入模型前替换掉
- **格式归一**：去掉多余空白、统一换行、规范编码

这三项都是脏活，但线上“偶发异常”里有相当一部分根源在这里。

## 五、提示词、检索、微调：什么时候才需要微调

**默认顺序是：提示词 → 检索增强 → 输出约束 → 微调。**

大部分业务问题，前三层已经能解决。微调应该是在下面这些情况才考虑：

- **格式稳定性**成了瓶颈，怎么改提示词都有小概率跑偏
- **领域术语和表达习惯**模型学不会（医疗、法律、内部黑话）
- **成本**：用一个微调过的小模型替代大模型调用
- **延迟**：小模型更快

**微调不适合注入频繁变动的事实。** 公司制度每季度都变，用微调去记是不现实的——那属于检索的活儿。微调擅长的是**稳定的领域知识、风格和格式**。

**输出约束是性价比最高的一层。** 用结构化输出（如 Pydantic / JSON Schema）约束返回结果，能同时拿到格式稳定和解析可靠两个好处，成本几乎为零。

## 六、部署与降级：把推理当成有 SLA 的后端

模型服务会超时、会限流、会 5xx。这些不是异常，是常态。

**必须提前准备的四件事：**

- **超时**：区分连接超时和整体超时，并给流式场景单独设定
- **重试**：只对可重试错误重试（限流、5xx），且要带指数退避和抖动；**参数错误不要重试**
- **熔断**：连续失败后暂时切断，避免雪崩
- **降级**：返回兜底文案、走规则引擎、或转人工，而不是让用户看到一个报错

**缓存是成本优化里最立竿见影的一招。** 摘要、标签、分类这类结果是可复用的，按**输入内容的哈希**做缓存键：

```python
key = f"summary:{sha256(normalized_text.encode()).hexdigest()}"
```

注意缓存键要用**归一化之后**的内容算，否则多一个空格就缓存不命中。

## 七、可观测性：至少看四类信号

模型服务的“健康”不能只看接口成功率。**至少观察这四类：**

1. **成功率**：区分模型返回错误、超时、输出解析失败
2. **延迟分位**：看 P50 / P95 / P99，平均值会掩盖长尾
3. **Token 成本**：按任务类型和模型分别统计，追踪异常尖峰
4. **质量抽检**：定期人工抽查输出，这是唯一能发现“静默变坏”的手段

**模型升级必须走回归集。** 厂商发布新版本、“效果更好”的宣传，都不能作为直接上线的理由。跑一遍冻结的评测集，对比分数，再灰度。

**“静默变坏”是最危险的情况**：接口全部 200，延迟正常，但输出质量悄悄下降。没有抽检和回归集，这只能等用户投诉才发现。

## 八、容易踩的坑

**把模型当函数调用，不做超时和重试。** 线上流量一大，第一次遇到限流就雪崩。

**提示词里没给“不知道”的出口。** 模型遇到盲区时倾向于编造，而不是承认不知道。明确允许它说“根据提供内容无法判断”，能显著降低幻觉。

**不约束输出格式，靠正则从自然语言里抠字段。** 脆弱且难维护，改成结构化输出能省掉大量解析代码。

**没有缓存，同样的内容反复付费。** 尤其是摘要和标签这类确定性高的任务。

**只看平均延迟。** 平均 800ms 可能意味着 P99 是 8 秒，而用户遇到的是后者。

**模型一升级就全量切。** 效果变化没有回归集兜底，出问题只能回滚重来。

## 小结

工程化的目标**不是把模型接进系统**，而是让业务在模型波动时仍然可预期：

1. **先定边界**：错误容忍度、延迟预算、单次成本上限
2. **封装成服务**：业务不直接依赖厂商，重试/缓存/降级/埋点都在这一层
3. **按任务分布选型**，保留切换能力，大模型小模型分层使用
4. **冻结评测集**，所有改动都跑回归
5. **提示词 → 检索 → 输出约束 → 微调**，按这个顺序投入
6. **超时、重试、熔断、降级、缓存**全部提前准备
7. **监控成功率 / 延迟分位 / 成本 / 抽检质量**，模型升级走灰度

先把边界画清楚，再谈更复杂的智能体与多模型编排——否则只是把不确定性放大。幻觉的根因与分层治理见 [大模型幻觉：成因、分类与四层解法](article.html?slug=llm-hallucination)，超时重试的具体写法见 [大模型 API 重试与超时](article.html?slug=llm-api-retry-timeout)。
