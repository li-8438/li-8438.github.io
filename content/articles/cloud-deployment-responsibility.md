服务在一台云主机上跑得好好的。某天你要「上云」——加个负载均衡、把数据库换成托管版、日志接到云厂商的日志服务、加一层对象存储。功能一行没改，账单从三百涨到两千三。

你去翻明细，每一项看起来都不贵：负载均衡按小时、托管数据库按规格、日志按写入量、对象存储按存储量加请求数、快照按容量。没有哪一项是「黑」的。但合起来就是解释不通。

问题不在厂商定价，在于**你以为自己买的是「服务器」，其实买的是「不用管什么」**——而这个东西的价格，从来没在你的成本模型里出现过。

## 一、部署的本质：一次责任边界的采购

「云端部署」这个词被用得太松，导致一个根本问题没被问出来：**我到底把哪些运维责任卖给厂商了？**

从「什么都自己管」到「什么都不用管」，是一条连续的光谱：

| 形态 | 厂商管 | 你管 | 典型代表 |
|---|---|---|---|
| 自建机房 | 无 | 全部（电力、制冷、网络、硬件） | 自建 IDC |
| 裸金属 / 云主机 | 电力、网络、硬件 | OS、运行时、扩缩容、高可用、补丁 | ECS / EC2 / Hetzner |
| 托管容器 | 编排层、节点 | 镜像、调度策略、容量规划 | EKS / ACK / GKE |
| Serverless 容器 | 编排 + 节点 + 伸缩 | 镜像 + 并发配置 | Fargate / Cloud Run |
| 函数 / 全托管 | 上面全部 + 运行时扩容 | 业务代码 | Lambda / 函数计算 |
| 全托管 SaaS | 连业务逻辑都包了 | 只配置 | 托管 RAG / 托管搜索 |

看这张表要抓住一件事：**往右走，你不是在「省钱」，你是在「买保险」。**

厂商收的托管溢价，本质是「凌晨三点不被叫醒」的保费。而保费该不该付，判据不是「方不方便」，而是**这件事出错的代价有多大**。

一个具体的分界线：数据库。

自己装 MySQL 在云主机上，省的是托管差价（公开报价里，托管数据库相对自建通常有 2–3 倍溢价）。但如果你的业务是「数据丢了公司就完了」，那 2–3 倍买的不是配置面板，是主备切换、是 PITR、是有人在你睡觉时盯着。**这笔钱该花。**

反过来，一个内部定时任务，跑挂了最多被同事在群里问一句。给它配托管编排 + 多可用区，你买的是你根本不需要的保险。

所以第一个决策问题不是「用哪个云」，是：

> **这件事如果我亲自兜底，最坏会怎样？**

答案决定你该停在光谱的哪一格。

## 二、选抽象层，其实是在选你的利用率曲线

责任光谱是定性判断，但抽象层还有个定量后果：**它决定了你为「没人用的时候」付多少钱。**

2026 年的实测数据把这件事说得很清楚。同样是 10000 RPS 的持续负载：

| 指标 | 函数（Lambda 类） | 容器（Fargate 类） |
|---|---|---|
| 单 vCPU 可持续吞吐 | 约 2,100 RPS | 约 8,900 RPS |
| 每百万请求单价 | 约 $0.20 | 约 $0.05 |
| 冷启动 p99（1GB 内存） | 约 300–420 ms | 常驻无冷启动（任务启动 8–15 s） |
| 10000 RPS 月成本 | 约 $12,480 | 约 $2,960 |

**4.2 倍的差距，来源不是单价，是计费模型的错配。**

函数按「调用」计费，它假定你会闲着；容器按「时间」计费，它假定你会一直忙着。一个 24 小时满负荷的服务，用按调用计费的模型去买，等于替厂商的灵活性买单。

行业内比较一致的经验分界点在**持续 CPU 利用率 30%–40%** 附近：低于它，按需付费的模型更划算；高于它，固定容量更便宜。换成调用量，典型形态下大约是每天 500 万到 1000 万次。

这里有个最容易被忽略的反转：**冷启动的真正代价不是那 400 毫秒，而是你为了 400 毫秒所买的东西。**

如果你的接口要求 P99 在 100ms 以内，那函数就没法纯按需——你得开预热实例（provisioned concurrency）或最小实例数。而这两样都是**按常驻容量计费**的。公开报价里，把 `min-instances` 打开，账单常常是被抬到 2–3 倍。

于是出现一种荒谬的状态：**你按 serverless 的名义，买了一份固定容量，还多付了一层抽象的成本。**

所以冷启动这个问题的正确问法不是「它有多慢」，而是「我对延迟的要求，会不会让我必须放弃按需计费」。如果是，那 serverless 的经济性从一开始就不存在，你该坦诚地去买容器。

那函数还剩什么场景？三类，而且都很值：

1. **尖峰与不可预测**：营销活动、webhook 接收器、每天跑十分钟的批处理。峰谷差 5–10 倍时，按需计费的收益是真实的。
2. **胶水代码**：对象存储事件触发、定时任务、把 A 格式转成 B 格式。为一个 30 行的转换函数维护一套容器编排，是纯粹的运维浪费。
3. **边界与低延迟入口**：跑在 V8 isolate 上的边缘函数几乎没有冷启动。

一句话总结这一节：**先看利用率曲线，再看技术栈。** 抽象层选错，后面所有优化都是在给一个错误的前提打补丁。

## 三、账单里最贵的，通常不是机器

回到开头那个「三百涨到两千三」的场景。如果真的去拆，钱通常不在算力上，而在这四样：

**一、出网流量（egress）。**

这是云成本里最反直觉的一项：**它随你的成功而增长。** 用户越多、返回的数据越多，这项就越大，而它和你的服务器规格完全无关。

2026 年的公开报价大致是：AWS 前 10TB 约 $0.09/GB 并阶梯下降，Azure 约 $0.087/GB，GCP 约 $0.08–0.12/GB 且亚太更高，**跨云出网约 $0.12/GB**。

把它换算成感觉：

- 一个月 100TB 出网 ≈ **$7,000–9,000**，与算力和存储无关
- 1PB 数据集从对象存储搬出来 ≈ **$90,000**
- 训练语料那种量级（240TB）搬一次 ≈ **$15,000 以上**

注意契约的不对称：**入网免费，出网收费。** 进来的数据不要钱，是为了让你没有顾虑地进来；出去要钱，是为了让你在出去之前多算一遍。这个设计有一个更准确的名字，叫**数据重心（data gravity）**——当数据重到搬不动，算力就得搬到数据旁边，于是你留在原地不是因为架构好，是因为搬走的成本太高。

顺带说一个可用的结构：如果出网是你的主要成本项，那**自带免费/不计量出网的存储与 CDN**（例如 R2 这类）值得单独评估。这不是「谁更便宜」的问题，是把一项随规模线性增长的成本直接删掉。

**二、闲置。**

按时间计费的资源，在你没流量的时候照样收费。托管数据库 7×24 计费、负载均衡按小时、NAT 网关按小时加流量——一个日活很低的内部系统，光是「基础设施底噪」每月就能几百块。

**三、按调用/按主机计费的可观测性。**

这一项最隐蔽。APM 和日志服务在很多档位上是**按主机或按调用**收费的，于是它会**随流量线性增长**，而你的算力账单在弹性伸缩下并不会。很多人第一次发现「监控比业务还贵」就是在这里。

**四、为「保险」重复付费。**

同一条链路上，你把网络、WAF、日志、密钥、镜像扫描各买一份托管服务，如果团队只有两三个人，这些服务的配置成本和月度费用会叠加成一块固定开销——它们单看都不贵，加起来就是那多出来的两千块。

**可操作的判据：把出网、闲置、可观测性三项单独列行，不要混进「云服务费」。** 混在一起的结果就是开头那个场景——金额看得出，原因说不出。

## 四、云回迁：不是意识形态，是算术

2026 年有个明显的趋势：把负载从公有云搬回自建或托管机房（colocation）的「云回迁」不再是边缘主张。推动它的是三股力：

**一、可预测负载在替弹性付溢价。** 弹性伸缩的价值来自不确定性。一个负载曲线平稳的系统，买的就是一个用不上的能力。（a16z 早前提出的「云悖论」讲的就是这件事：重负载业务的毛利率被基础设施吃掉一大块。）

**二、出网费卡住了商业模式。** 有公开的经验判据：**当出网费用超过总账单的 30%，回迁在财务报表上就从「可选项」变成「必须项」。**

**三、GPU 的自有回报周期进入了可接受区间。** 一台 8 卡 H100 的云实例按需报价约 $32–40/小时，80% 利用率跑满一年约 **$27 万**；而一台二手同规格服务器加托管费用大约 **$11–13 万**，**4–6 个月回本**，之后推理成本下降八成以上。这也是 37signals 公开那笔账（五年省下约 700 万美元级别）能被广泛引用的原因——不是口号，是能算的。

但**回迁不是普遍正确的**。适合回迁和适合留在云上的画像是清晰互补的：

| 适合迁出（自建/托管机房） | 适合留在云上 |
|---|---|
| 资源需求可预测，规划周期 3 年以上 | 峰谷差 5–10 倍，弹性产生真实收益 |
| 出网占总账单 30% 以上 | 出网占比很低 |
| 重度使用托管数据库（溢价最高的品类） | 产品还在验证期，现金流比优化重要 |
| GPU 利用率稳定（自有回本 4–6 个月） | 重度依赖云原生服务（绑死后回迁等于重写） |
| 有 SRE / 运维能力 | 运维人手缺口（事故成本会超过云溢价） |

我把这张表放在这里，是为了标记一个立场：**云回迁不该是立场之争。** 同一个团队，把可预测的常驻负载放自建、把尖峰放云上，是完全合理的混合形态。真正该避免的是两种教条：把「上云」当现代化标签，和把「回迁」当技术审美。

## 五、上云第一步不是买机器，是无状态化

这是全篇我觉得最该被记住的一节。

很多人对「上云」的想象是：开一台云主机，装环境，把服务放上去。这在功能上没问题，但在架构上是一次**昂贵的原地踏步**——你把单机运维搬到了一个租金更高的地方，还额外买了一份用不上的弹性。

因为**弹性伸缩的前提是无状态**。

负载均衡把请求打到哪台机器都行，这件事成立的条件是：任何一台机器都不持有「只有它有」的东西。会话、上传的文件、本地缓存、定时任务的状态——只要有一个留在本地磁盘上，横向扩容就会出问题，缩容就会丢数据。

**状态外置是上云的入场券，不是优化项：**

| 状态类型 | 外置到哪 |
|---|---|
| 会话（Session） | Redis 之类的内存服务 |
| 用户上传的文件 | 对象存储 |
| 业务数据 | 托管数据库（或至少独立的数据库实例） |
| 构建产物、模型权重 | 对象存储 / 镜像仓库，不要打进镜像 |
| 定时任务、后台作业 | 独立的调度器或消息队列，不要靠容器里的 cron |

反过来说，一张很实用的自检表是：**把任意一台应用实例直接删掉，服务会怎样？** 如果答案是「请求被分到别的实例，用户无感」，你的架构就绪了。如果答案是「一部分用户掉线、上传的文件找不到了」，那还没到上云那一步。

按这套标准做下来的应用，和所谓「十二要素应用」高度重合——不是因为它是什么规范，而是因为那些条目本来就是在描述「可被随时替换的进程」长什么样。

## 六、上线前那几件「出事才想起」的事

工程前提之外，云端部署还有一批**默认值不安全的项**。它们的特点是：不出事时完全无感，出事时是新闻。按重要性排：

**一、最小开放的安全组。** 只开必要端口。数据库、缓存、管理后台一律不暴露公网。SSH 限制来源 IP。这一项能挡掉绝大多数自动化扫描。

**二、禁用密码登录，强制密钥。** 顺带说，改 SSH 默认端口属于「降低噪声」，不是安全措施——它挡不住有针对性的扫描。

**三、密钥不进代码仓库。** 用环境变量或云厂商的密钥管理服务。这一条是硬伤级：一旦密钥进了 git 历史，删文件是没用的，历史还在。

**四、备份必须演练过。** 「做了备份」和「能恢复」是两件事。3-2-1 原则（3 份副本、2 种介质、1 份异地）是针对「勒索软件加密了你的文件」和「误删了核心库」这两种场景的最后一道防线。关键是**定期真的恢复一次**——没演练过的备份等于没有备份。高敏感场景还可以开对象存储的防篡改（不可变备份），让被攻破的管理员账号也删不掉备份。

**五、监控要看对指标。** 只看 CPU 是不够的。真正会打死服务的是：**磁盘写满、证书到期、内存溢出、带宽打满**。这四个里任何一个都能让一个 CPU 极其健康的服务彻底不可用。

**六、基础设施即代码。** 这一条经常被当成「大团队才需要」。但真正的理由是那句朴素的话：**很多事故不是服务挂了，而是重装之后发现环境记不清、配置找不到。** 如果你的整个环境没法用一份代码从零重建，那你对它的掌握是假的。

我把它压缩成一个问题：

> **从零重建整个环境，你要多久？**

答案如果是「记不清了，可能一天」，那这套云端部署是脆的。如果答案是「跑一遍流水线，二十分钟」，才叫部署。

## 七、我的判断顺序

把上面几节压成一套可以照着问的流程：

1. **先问责任边界**：这件事我兜底的最坏后果是什么？决定该买多少保险。
2. **再看利用率曲线**：持续利用率低于 30%–40% 倾向按需，高于它倾向固定容量。
3. **然后看延迟要求**：如果 P99 要求逼你开常驻容量，就承认自己是容器负载，别付两层的钱。
4. **单独算出网、闲置、可观测性**：这三项决定账单的斜率。
5. **做完无状态化再上云**：这是能否弹性的前提，不是上线后的优化。
6. **最后才是选厂商**。云厂商的差异远小于架构选型的差异——比价之前先把前面五步做完。

顺便说，比价本身也有个常被忽略的维度：**长期总成本 ≠ 首单价格**。首单折扣是获客成本，你的成本曲线在第二年、在你流量翻倍之后才真正显形。

## 八、常见误区

**「上了云就自动高可用。」** 不会。默认配置下，你的云主机仍然是一个单点。高可用是**多可用区 + 无状态 + 健康检查剔除**换来的，不是买机器送的。

**「serverless 一定更便宜。」** 只在低利用率下成立。高吞吐场景下，实测数据是反过来的，差距可以到 4 倍。

**「云 = 免运维。」** 责任是**转移**，不是消失。你要管的东西从「装 Nginx」变成「配安全组、管密钥、看账单、设备份策略、盯证书到期」。责任从体力活变成了判断题。

**「出网费可以忽略。」** 如果你的服务返回的是文本，它确实小。如果返回的是图片、视频、模型、大数据集，它可能就是你账单里最大的一项——而且它随增长放大。

**「以后再说回迁的事。」** 这恰恰是最该提前想的一条：**在架构里保留可搬性**（容器化、别重度绑定单一厂商的专有服务、状态有明确出口）。不是为了搬，是为了保留选择权。选择权本身就有价值。

## 小结

云端部署的每一次决策，本质上都是同一个问题的不同问法：

> **这份责任我买断，还是自己扛？**

抽象层是这个问题的答案，账单是它的价格，无状态化是你能选它的前提。

三个我认为最值得留在脑子里的数字：**出网超过账单 30% 时回迁从可选项变成必须项**；**持续利用率 30%–40% 是计费模型的分水岭**；**GPU 自有的回本周期已经进入 4–6 个月**。

以及一个朴素的自检：**把任意一台实例删掉，用户会不会有感；从零重建整个环境，你要多久。** 这两个问题答好了，你的云端部署就已经超过大多数人。
