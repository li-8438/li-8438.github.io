先算一笔账，因为它推翻了大多数人做向量数据库选型时的出发点。

一个典型的端到端 RAG 请求，耗时大约 **300 毫秒**。拆开看：

| 环节 | 耗时 | 占比 |
| --- | --- | --- |
| 生成查询向量的 embedding | 约 90 ms | **约 30%** |
| 大模型生成答案 | 约 200 ms | **约 67%** |
| **向量库检索（pgvector）** | **约 5-8 ms** | **约 2%** |

**你换一个更快的数据库，省下 3 毫秒，等于把总延迟改善了百分之一——同时把运维面积翻了一倍。**

这不是说基准测试没意义。它们的意义在曲线顶端：当你真的在千万级向量上运行时，这些差异才从噪声变成信号。但对绝大多数团队来说，数据库不是你的延迟问题，**embedding 管道才是**。

## 一、2026 年的格局：先搞清楚谁在哪

| 方案 | 强项 | 适合什么 |
| --- | --- | --- |
| pgvector | 跑在现有数据库里、支持事务、免费 | 1000 万向量以下，且 Postgres 已经是你的记录系统 |
| Pinecone | 托管、serverless、运维成熟 | 中大型企业，不想背运维 |
| Qdrant | 开源、payload 过滤强、性能好 | 自建或托管，过滤型查询多 |
| Weaviate | 开源、原生混合检索 | 想要类 SQL 控制力且混合检索是核心 |
| Milvus / Zilliz | 十亿级规模、GPU 加速 | 超过 1 亿向量 |
| Elasticsearch / OpenSearch | 混合检索与日志同引擎 | 已经在用 ES 做搜索 |
| LanceDB | 原始数据和向量放一起 | 多模态、AI 流水线 |

一个国内视角的粗略分布（2026 年新建 AI 知识库项目）：**Milvus 及 Zilliz Cloud 约 35-42%，pgvector 约 25-32%，Elasticsearch 向量字段约 15-20%**，其余是 Redis Vector、DashVector、Weaviate 等。

## 二、什么时候你并不需要独立的向量数据库

这是本篇最想说清楚的部分，因为**最常见的错误不是选错库，是过早引入一个库。**

满足下面任意一条，就该从 pgvector 起步：

- **向量规模在 1000 万以下**（保守一点：500 万以下基本无争议）
- 业务数据已经在 PostgreSQL 里，你希望能跟元数据做 JOIN
- 团队不想再维护一个组件
- 你还在验证产品有没有人用

pgvector 的隐性优势经常被低估：**检索和你的业务数据在同一个事务边界里。** 混合检索完之后可以直接 JOIN 业务表、按租户过滤，全部在一条 SQL 里完成——这在独立向量库里是做不到的。

```
-- 混合检索 + 业务过滤 + JOIN，一条 SQL 搞定
SELECT a.id, a.title, a.body,
       0.6 * (1 - (a.embedding <=> :query_vec))        -- 稠密得分
     + 0.4 * ts_rank_cd(a.tsv, plainto_tsquery(:q))    -- BM25 得分
       AS score
FROM articles a
JOIN tenants t ON t.id = a.tenant_id
WHERE a.tenant_id = :tenant          -- 租户隔离
  AND a.valid_until IS NULL          -- 只要还生效的版本
ORDER BY score DESC
LIMIT 20;
```

成本上也很直白。**pgvector 在托管 Postgres 上每百万向量每月的存储成本大约在 5 到 20 美元量级**，而独立向量库通常要高出一个数量级——更别说多出来的运维人力。

**2026 年最常见的失误是过度采购**：为只有 200 万向量的试点买了一个专门的向量数据库，然后花六个月建设本可以免费获得的运维能力。

## 三、什么时候你真的需要

反过来说，出现下面任何一条，就该认真考虑专用方案：

- **单索引超过 5000 万到 1 亿向量**
- **持续 QPS 超过 Postgres 的 IOPS 承受范围**（几百 QPS 以上）
- 需要多区域复制来降低读延迟
- 需要 GPU 加速的检索
- 查询时需要对元数据进行强过滤（租户 ID、时间范围、ACL），且过滤选择性很高

判断的时候注意一点：**pgvector 配 HNSW 索引在单表 5000 万向量以内依然可用**，超过这个量级再评估 Qdrant、Weaviate 或 Pinecone。中间地带（500 万到 5000 万）用 Postgres 撑半年、同时设计好迁移路径是可以接受的——**但别把 PG 无限垂直扩容到 512GB 内存。**

## 四、混合检索已经是标配，不是加分项

这一点在 2026 年基本没有争议了：**BM25 + 稠密向量 + RRF 融合是默认形态。**

原因很实际。**纯向量检索对精确标识符几乎无能为力**——产品型号、错误码、函数名、CVE 编号，这些字符串在嵌入空间里彼此高度相似。而它们恰恰是企业知识库里最常见的查询。

有个基准可以说明差距：**混合检索 + rerank 的 Recall@5 是 0.816，纯稠密检索只有 0.587。**

需要知道的一个取舍：**pgvector 没有原生 BM25。** 你要么装 pg_search / ParadeDB 这类扩展，要么自己把向量距离查询和 `tsvector` 全文查询拼起来、手写 RRF 融合。这是可行的（很多生产系统就这么干），但它是**你要拥有和维护的代码**，不是一个开关。

如果混合检索是你产品的核心，把这个工程量算进去。

另一个提醒：**在确认真的需要之前，别为了混合检索去迁移数据库。** 拿 50 条真实 query，分别用纯向量和混合融合跑一遍、打分。如果提升微乎其微，那你是在为用不上的功能付迁移成本和锁定成本。如果提升很明显——技术文档、代码、含大量精确标识符的语料通常如此——那才是选择 Qdrant 或 Weaviate 的具体理由。

## 五、reranker 的收益通常大于换库

这条在第二、三节之间，但值得单独拎出来：**加一个 cross-encoder reranker 对答案质量的提升，通常大于换一个更快的向量库。**

原因是两者解决的是不同环节的问题。数据库决定"多快能找到候选"，reranker 决定"候选里哪些才是真的相关"。前者影响 2% 的延迟，后者影响召回质量。

一个务实的流水线：

1. 稠密召回 top 50
2. 稀疏（BM25）召回 top 50
3. RRF 融合
4. **cross-encoder rerank 到 top 5-10**
5. 送入生成

## 六、一条可执行的选型路径

不要 Day 1 就做架构决策。按这个顺序走：

**第一步：估算 12 个月后的向量条数和 QPS。** 不是今天的，是 12 个月后的。

**第二步：确认是否必须混合检索。** 2026 年的答案几乎总是 Yes，但还是要用真实 query 验证一次。

**第三步：盘点现有运维能力。** 你们有没有能扛住 Postgres / ES / Milvus 的人？这一条往往比技术指标更能决定结局。

**第四步：用生产 query 样本做 POC，测 Recall@K。** 注意是 **Recall@K，不是延迟**。延迟问题在上面那张表里已经算清楚了。

**第五步：三个月后用数据决定是否迁移。** 签合同前明确 re-index 和扩容的 SLA。

## 七、容易踩的坑

**在清洗知识库之前就上集群。** 这条几乎每份报告都会提，因为几乎每个团队都会犯。垃圾 chunk 进去，任何数据库都救不回 ROI。**先治理知识，再扩容硬件。**

**换 embedding 模型要全库重建。** 不同模型的向量空间不可比。混用两个模型写入同一个索引，检索结果会毫无意义。统一用一个（bge-m3 或通义 text-embedding-v3 之类），并给将来的升级预留 re-index 窗口。

**无索引的标量过滤 + 大规模向量 = 秒级 P99。** 租户 ID、时间范围这些过滤字段必须建索引。这是从"几十毫秒"掉到"几秒"的最常见原因。

**忘了向量能被反推。** 向量不是哈希，它可以被反推出原文片段的近似信息。敏感库必须做静态加密，租户级 ACL 过滤必须做——**配置错误导致的跨租户泄露是这个领域最常见的事故类型之一。**

**低估了多模态带来的膨胀。** 2026 年下半年图文联合检索开始起来，维度从 768 涨到 1024-2048，存储需求乘 2-3 倍。提前规划冷热分层（SSD 存热数据、对象存储放冷数据）能避免紧急扩容。

**CDC 延迟导致读到旧 chunk。** 一致性问题在 RAG 里表现为"答案看起来很合理但是过期的"，这种错误最难被发现。

## 小结

如果只留一句话：

> **数据库是管道，策略才是胜负手。真正的竞争优势不是你选了哪个向量库，而是你的 embedding 质量、数据新鲜度，以及在把结果送给 LLM 之前你怎么重排和后处理。**

具体到行动上，我的建议是**从 pgvector 起步，带着评测，让数据告诉你什么时候该换**。这个顺序的好处是：如果产品没跑起来，你只损失了很小的成本；如果跑起来了，你手上已经有了做迁移决策需要的真实数据——而不是 Day 1 的猜测。
