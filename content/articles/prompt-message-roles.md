调用大模型 API 时，我们传的不是一个字符串，而是一个消息列表，每条消息带一个 `role` 字段。很多初学者把所有内容一股脑塞进 `user` 里，提示词时不灵——理解三种角色的分工，是写出稳定提示词的前提。

## 一、三种角色各自的职责

### System：定框架

System 消息用来**设定对话的全局方向和行为模式**。它在整个会话中持续生效，即使后续对话里不再重复，模型也会一直遵守。

它的典型用途有三类：

- **设定背景与规则**：如"你是一个专业翻译，只回答与翻译相关的问题"
- **调整风格与格式**：指定语气（严肃 / 幽默）、输出格式（分点 / Markdown / JSON）、内容限制
- **约束任务流程**：规定复杂任务必须按哪些步骤完成

### User：给输入

User 代表真实用户的输入，是驱动对话的核心。它负责提出问题、补充信息、修正模型行为。

一个容易忽略的用法：**User 消息也能承担部分"控制"职责**。比如在多轮对话里追加一句"用更简单的语言重说一遍"，就是在通过 user 消息间接调整输出。

### Assistant：模型的回复

Assistant 是模型生成的回复内容。但在多轮对话里，它还有两个重要作用：

- **提供上下文**：历史 assistant 消息让模型知道之前说过什么，保证连贯性
- **做示范**：你可以**人工构造**一条 assistant 消息，用来给模型示范"遇到这类问题应该这样答"。这是 Few-shot 和格式约束的常用手法，也是后面讲的结构化输出的基础。

### 三者的优先级

笼统地说：**最近的 user 指令 > 初始的 system 设定 > 历史 assistant 内容**。

但这个顺序不是绝对的，不同模型对 system 的权重处理不同——有些模型对 system 的遵循度更高，能更稳定地执行长期指令。这也是为什么"换模型后提示词要重新调"是常态，不是玄学。

## 二、System Prompt 的四段式写法

看一个具体案例。需求是：从用户粘贴的快递信息里抽出姓名、电话、地址，输出 JSON。

```
你是一个快递信息提取专家，能够根据用户输入的快递地址、姓名、手机号信息把对应的实体抽取出来，
并以 JSON 格式返回。

示例输入：
"""
收件人，138-1234-5678
广东省深圳市南山区科技园南区高新南一道 1000 号某大厦 18 层 1806 室
"""

示例输出：
{
  "name": "收件人",
  "phone": "13812345678",
  "address": "广东省深圳市南山区科技园南区高新南一道 1000 号某大厦 18 层 1806 室"
}

约束：
1. 对于用户的输入，你只返回上述 JSON 格式，不要返回任何其他内容。
2. 手机号统一去除分隔符，只保留数字。
3. 如果某项信息缺失，对应字段返回空字符串，不要省略字段。
```

这段提示词可以拆成四个部分，缺一不可：

| 段落 | 作用 | 缺失后果 |
| --- | --- | --- |
| **角色设定** | 圈定能力范围和语域 | 输出风格不稳定，时详时略 |
| **任务描述** | 说清要做什么 | 模型猜你的意图 |
| **示例（Few-shot）** | 用样例锁定输出格式 | 格式飘忽，解析失败 |
| **明确约束** | 规定边界情况怎么处理 | 遇到异常输入就胡来 |

其中**"只返回 JSON，不要任何其他内容"**这句看着简单，实际极其关键。不加这句，模型很可能在 JSON 前后加上"好的，以下是提取结果："和"希望对你有帮助"——你的 `json.loads()` 直接崩掉。

完整调用：

```python
import dashscope

dashscope.api_key = "your-api-key"

system_prompt = """...（上面的四段式提示词）..."""

user_input = """
联系人
151-9876-5432
北京市海淀区中关村大街 1 号某大厦 8 层 805 室
东西是一份文件，已经封装好了。寄普通快递就行，麻烦寄出后把单号发我一下，谢谢啦！
"""

response = dashscope.Generation.call(
    model="qwen-max",
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_input},
    ],
)

print(response.output["text"])
```

注意 user 输入里有一句"寄普通快递就行，麻烦寄出后把单号发我一下"——这是真实场景里常见的**噪声**。好的 System Prompt 要让模型明白：这些是收件人的附言，不是给模型的指令，忽略即可，只抽字段。

## 三、为什么内容放 system 比放 user 更稳

实践中有个普遍现象：**同样的约束写在 system 里，比写在 user 里遵守得更好**。

原因有两层：

**第一，位置带来的注意力差异。** 模型对输入开头和结尾的内容关注度更高（中间部分容易"丢失"，也就是常说的 lost in the middle）。system 消息永远在最前面，天然占据优势位置。

**第二，训练方式决定的语义权重。** 在指令微调阶段，system 消息被训练为"全局规则"，user 消息被训练为"本次请求"。模型学到了这个区分——system 里的规则适用于所有轮次，user 里的话只对这一轮有效。

所以分工建议是：

- **稳定的、跨轮次生效的**放 system：角色、输出格式、安全边界、业务口径
- **变化的、单次生效的**放 user：具体问题、待处理的数据、临时要求

## 四、生产环境的三个实践要点

### 提示词要像代码一样版本管理

提示词会频繁改动，而每次改动都可能让线上效果退化。所以必须：

- 把提示词抽成独立的模板文件或常量，**不硬编码在业务代码里**
- 每次修改留痕，能回滚
- 建立回归测试集：准备几十条典型问题，改完提示词跑一遍，对比输出变化

一个真实踩坑场景：为了让回答更详细，你在 system 里加了句"请尽可能详细地回答"。结果模型的回答变长了，但也开始编造细节——因为你没同时收紧"只基于给定上下文"的约束。没有回归测试，这种退化很难当场发现。

### 敏感信息不要写进提示词

提示词里有 API 密钥、数据库连接串、内部域名，是常见的安全事故。原因是：

- 提示词可能被记录在日志、链路追踪系统里
- 模型输出中可能泄露提示词片段（提示词泄露攻击）

正确做法是：提示词里只放占位符，真实值在代码里注入；日志打印时对提示词脱敏。

### 多轮对话要控制上下文长度

每轮对话都要把历史消息全量传给模型，token 消耗是随轮次**线性增长**的，费用也跟着涨。

常见的压缩策略：

- **滑动窗口**：只保留最近 N 轮
- **摘要压缩**：定期让模型把历史对话总结成一段摘要，用摘要替代原始消息
- **摘要 + 最近消息**：两者结合，既保留全局要点，又保留最近细节

最后这种是工业界最常用的方案——我在 RAG 项目里用的就是"历史摘要 + 最近 N 条消息"的组合。

## 小结

三种角色的分工可以概括成一句话：**System 定框架 → User 给输入 → Assistant 出回复**。

写好 System Prompt 的核心是用四段式结构把话说全：角色 + 任务 + 示例 + 约束。其中"示例"决定格式稳定性，"约束"决定边界情况的表现。

上生产时记住三条：提示词要版本管理和回归测试、绝不写敏感信息、多轮对话要主动压缩上下文。
