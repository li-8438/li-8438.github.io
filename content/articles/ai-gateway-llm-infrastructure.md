有一个架构组件，几乎所有把 LLM 真正跑起来的团队最后都会自己长出一个出来——不管他们一开始有没有意识到自己在做这件事。

它就是 **AI Gateway**。

不是因为大家爱造轮子，而是因为**直接调用模型厂商 API 这个做法，在原型阶段完全正确，在生产阶段会同时崩掉六个地方。**

## 一、直连为什么撑不到生产

| 症状 | 直连时的表现 |
| --- | --- |
| 无可见性 | 不知道哪个团队、哪个功能在烧钱，除非每个调用点都埋点 |
| 无韧性 | 厂商一挂，你全部 AI 能力一起挂 |
| 无成本控制 | 一个失控的循环或一行 bug，几分钟烧穿预算 |
| 重复劳动 | 每个服务自己写重试、缓存、错误处理 |
| 供应商锁定 | 换模型要改遍全站代码 |
| 密钥散落 | API key 散在各服务的环境变量里 |

这些问题的共同点是：**它们都是横切关注点**。而横切关注点的标准解法就是加一层。

一个现实背景：企业平均同时使用的 LLM 供应商数量已经到了 **3.4 家**。在这个数字下，"每个服务自己管自己的调用"基本不可维护。

## 二、Gateway 到底是什么：不是反向代理

一个常见的误解是把它理解成"给 LLM 加了个反向代理"。这个理解会让你少做很多事。

更准确的定位是：

> **AI Gateway = API Gateway + FinOps + 策略控制面。**

区别在于通用 API 网关不懂 token。它不理解什么叫输入/输出 token、什么叫 TPM 限流、什么叫 prompt 缓存、什么叫按模型计费。**这些语义是 LLM 特有的。**

一个请求的完整生命周期，通常穿过五层：

| 层 | 职责 | 典型失败模式 |
| --- | --- | --- |
| L1 Auth | API Key / OIDC / mTLS | 密钥泄漏 |
| L2 Route | model alias → provider | 路由到贵模型 |
| L3 Policy | 限流、预算、内容策略 | 预算穿透 |
| L4 Cache | 精确缓存 / 语义缓存 | 跨租户污染 |
| L5 Provider | 真正发起推理 | 上游 5xx |

这个表的右边一列值得多看两眼——**每一层都有它自己特有的失败模式**，而这正是它需要独立存在的原因。

## 三、五个核心能力

### 1. 路由：把"用哪个模型"从代码里拿出来

路由策略可以按不同维度触发：

| 策略 | 触发条件 | 例子 |
| --- | --- | --- |
| 静态别名 | 功能固定 | 客服机器人 → 小模型 |
| 延迟优先 | 有 p95 SLA | 区域就近 |
| 成本优先 | 非关键路径 | 路由到最便宜的档 |
| 能力优先 | 需要工具调用 | 路由到强模型 |
| 灰度 | 模型版本升级 | 5% → 25% → 100% |
| 合规 | 数据驻留要求 | 只走特定区域 |

关键收益是：**换模型从"改代码 + 全量回归"变成"改配置 + 灰度"。** 这在你每年要评估三四个新模型的时候价值极大。

### 2. 缓存：收益最大的一项，也是风险最大的一项

两种缓存：

**精确缓存**（按 prompt 哈希）：零误判，但只对完全相同的请求有效。

**语义缓存**（按 embedding 相似度）：命中率高得多，但需要仔细调阈值。

```python
class SemanticCache:
    def __init__(self, redis_url, similarity_threshold=0.95):
        self.redis = Redis.from_url(redis_url)
        self.threshold = similarity_threshold

    def get(self, prompt):
        q_emb = self._embed(prompt)
        for key in self.redis.scan_iter("cache:embedding:*"):
            cached = json.loads(self.redis.get(key))
            if cosine(q_emb, cached["embedding"]) >= self.threshold:
                return cached["response"]
        return None
```

**语义缓存有两个必须守住的边界：**

**一、缓存键必须包含 tenant_id。** 只按 messages hash 做键，会跨租户命中——这是把 A 客户的数据吐给 B 客户的最快方式。

```ini
cache_key = SHA256(tenant_id + model + normalized_messages + prompt_rev)
```

**二、受监管场景禁用。** 一个"相似但错误"的答案对信任的伤害，远大于一次缓存未命中。FAQ 类功能可以用，涉及政策、医疗、金融答案的不要开。**阈值要保守。**

### 3. 限流与预算：防止几分钟烧穿

限流要在多个粒度上做：

| 粒度 | 指标 | 目的 |
| --- | --- | --- |
| 租户 | 每日金额、TPM | 防止单点失控 |
| 功能 | RPS | 控制特定功能的成本 |
| 用户 | 并发 | 公平分配 |
| 全局 | 上游 TPM | 硬顶 |

一个容易搞错的实现细节：**429 有两种语义，处理方式完全不同。**

- **网关侧的 `budget_exceeded`**：不可重试。重试只会让它继续超。
- **上游厂商的 `rate_limit`**：指数退避 + 切换到 fallback 链。

把这两种混为一谈，是最常见的浪费来源。

### 4. Fallback 与熔断：让调用方看不见故障

设计目标是：**调用方只说"我要一个摘要"，至于这个摘要是主模型给的还是 30 秒前故障期间由备用厂商给的，那是网关的一行日志，不是应用该关心的事。**

```yaml
# 每种任务类型配一条有序链
task_chains:
  summarization:
    - provider: azure/gpt-4o-mini
    - provider: bedrock/claude-haiku
    - provider: openai/gpt-4o-mini
  complex_reasoning:
    - provider: anthropic/claude-opus
    - provider: openai/gpt-5
```

一个关键设计：**每条链的第二个条目必须来自不同的厂商。** 否则一次区域故障会同时打掉整条链。

配套熔断：短时间内连续失败就跳闸，把该厂商的全部流量切到 fallback，直到探测请求成功。

### 5. 成本归因：没有它，你连问题在哪都不知道

每次请求落地一条结构化日志：

```
tenant_id, feature, task_type, model_requested, model_actual,
tokens_in, tokens_out, latency_ms, cache_hit, failover_events, cost
```

这一条流能回答那些原本很痛的问题：哪些租户在当前定价下不赚钱？哪个功能在烧 token 账单？上周二的延迟尖峰是你们的代码还是厂商？真实缓存命中率是多少？

**注意留存策略要从第一天就定**：prompt 里含客户数据。token 计数和元数据可以长期存，prompt 和响应体按 DPA 决定短期留存、脱敏或不存。

## 四、什么时候你其实不需要它

这一节和前面同等重要，因为**过早引入网关是另一种浪费**。

明确的判断标准：**以下四条中至少两条为真，网关才划算。**

- 有多个功能在调用 LLM
- 你按租户计费或做预算
- 你用了不止一家供应商
- 模型选择变化频繁到硬编码已经很痛

**一个功能、一家供应商、一个团队 → 直接调，把 fallback 写在应用代码里。**

时机上有个不对称值得记住：

> **过早引入，你多一跳网络和一个要运维的服务，换来一套你还没有的策略；过晚引入，你要迁移五个各自长出脾气的调用点。后者比前者痛得多。**

## 五、2026 年的格局：两个家族

市场按"从哪来"分成了两派：

**LLM 优先**：一开始就是多模型统一 API，后来才长出策略能力。
LiteLLM（开源、provider 目录最全）、Portkey、OpenRouter（托管）、Cloudflare / Vercel（边缘托管，自带缓存和消费上限）。

**基础设施优先**：把已有 L7 代理扩展成懂 AI 流量。
Kong AI Gateway、Envoy AI Gateway、Apigee、以及面向 agent 的 agentgateway。

选型启发式：

- 路由和策略层本身必须在内网、或者量大到付不起按请求计费 → 自建开源网关
- 想要缓存和预算执行但不想做运维 → 托管边缘网关
- 想让 REST 和 AI 流量走同一套治理 → 扩展现有 API 网关
- 想最快接上很多模型、数据驻留不是问题 → 托管多模型端点

一个务实的组合：**已有 Kong 的团队用 Kong 守边缘、LiteLLM 管模型层**，两者并存。

## 六、正在发生的演进：从 token 网关到 agent 网关

这是我认为接下来一年最重要的变化。

随着应用从"单次 LLM 调用"转向"调用工具的 agent"，网关开始支持 MCP：**代理 MCP server、认证工具访问、并且把给模型调用的限流和审计，同样施加到工具调用上。**

含义很直接：

> **网关正在成为 agent 所触碰的一切的策略咽喉点，而不只是它的 token 计费点。**

回看《88% 的 Agent 停在试点》里那些失败模式——工具输出投毒、灾难性动作、无限循环——会发现它们有一个共同的天然落点：**都在这一层可以被统一拦截和记录。**

值得注意的一个边界：**Agent 的步数预算应该放在应用层，不该放在网关。** 网关管 token 和预算，但它不理解"任务是否算成功"这个语义。

## 七、实施路径：从最痛的地方切入

不要一次做全。按痛点排序：

- **如果痛点是成本** → 先上预算执行 + 日志归因，路由后加
- **如果痛点是可靠性** → 先上路由表 + failover，预算后补

这个架构支持渐进采纳，因为**所有能力都挂在同一个咽喉点上**——先装哪个、后装哪个，都不会推翻前面的工作。

一个很实际的迁移路径：先用 10% 流量走网关，观察日志和成本数据，再逐步切到 100%。

## 八、容易踩的坑

**把智能写进客户端库。** 客户端库应该尽量"笨"。任何爬进客户端的智能最终都会和网关的策略不一致，然后你又回到了策略散落的状态。

**语义缓存键不含 tenant_id。** 前面说过，再说一遍，因为这是最容易出的事故。

**对 `budget_exceeded` 做重试。** 见第三节。

**把密钥留在应用里。** 网关的另一大价值是集中管理厂商 API key，让它们从源码和环境变量里消失。

**日志留存没有策略。** prompt 是客户数据，别无脑全量永久存储。

**Agent 步数预算放进网关。** 网关不理解成功语义，它只管 token。

## 小结

AI Gateway 这个模式之所以会自然长出来，是因为**它解决的不是某个具体问题，而是"LLM 调用的横切复杂性需要一个家"**。

值得记住的判断是：

> **一个优化良好的网关通常只增加不到 10-20 毫秒的开销，而这往往被缓存和延迟优化的路由抵消掉。真正的成本是运维它的人——所以要在你真的有策略需要执行时才引入。**

最后一点观察：这一层的存在，正在把"AI 工程"里真正稳定的部分沉淀下来。模型会换、厂商会变、价格会跌，但**鉴权、路由、预算、缓存、审计这五件事不会消失**。它们就是这一层的价值所在。
