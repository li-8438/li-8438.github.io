基础提示词解决"把需求说清楚"，进阶技术解决"让模型做得更准"。提示词工程里最常用的四种技术是 Zero-shot、Few-shot、Chain-of-Thought（CoT）和 Self-Consistency。

它们不是"越高级越好"的关系，而是对应不同难度的任务。用错档位，要么效果没提升还多花钱，要么该用的没用导致准确率不够。

## 一、Zero-shot：不给示例，直接问

Zero-shot 就是不提供任何示例，靠模型预训练知识直接完成任务。

```
将文本分类为中性、负面或正面。

文本：我认为这次假期还可以。
情感：
```

**特点**：高效（不用准备示例）、灵活（利用模型的通用知识）。

**适用**：模型在预训练时见过大量同类任务的场景——情感分类、简单翻译、摘要、实体识别这些，现代大模型的 Zero-shot 表现已经相当好。

**坑在哪**：Zero-shot 的输出**格式不受控**。你问情感分类，它可能回"正面"，也可能回"这句话的情感倾向是正面的"。要稳定格式，就得靠 Few-shot 或者前面讲的结构化输出。

## 二、Few-shot：给 1-3 个示例

Few-shot 就是在提示词里给出几个"输入 → 输出"的样例，让模型照着模式走。

```
你是一个翻译专家，请将英文句子翻译成中文。

示例：
英文：I like apples.
中文：我喜欢苹果。

现在请翻译：
英文：The weather is nice today.
中文：
```

**特点**：精准。示例直接消除了"你要什么格式"的歧义，输出一致性大幅提升。

**为什么有效**：模型并没有被"训练"，它是在做**模式识别**——从你给的样例里推断出任务规则，然后把同样的规则应用到新输入上。这叫 In-Context Learning（上下文学习）。

### 示例数量不是越多越好

实践中的经验值：

- **1-3 个示例**通常就够，边际收益递减得很快
- 超过 5 个，成本和延迟明显上升，准确率提升却很小
- 示例太多还有副作用：模型可能过度拟合示例的细节特征

### 示例的质量比数量重要得多

选示例的三个原则：

1. **覆盖边界情况**：不要全给最简单的样例，至少放一个难的、一个容易混淆的
2. **格式严格一致**：每个示例的输出格式必须完全相同，不一致会让模型无所适从
3. **顺序有影响**：最后一个示例对模型的影响最大（位置偏差），把最典型的放最后

### 一个真实的 Few-shot 案例

金融文本分类，要求把文本归到四个类别之一：

```python
class_examples = {
    "新闻报道": "今日，股市经历了一轮震荡，受到宏观经济数据和全球贸易紧张局势的影响。投资者密切关注美联储可能的政策调整。",
    "财务报告": "本公司年度财务报告显示，去年公司实现了稳步增长的盈利，同时资产负债表呈现强劲的状况。",
    "公司公告": "本公司高兴地宣布成功完成最新一轮并购交易，收购了一家在人工智能领域领先的公司。",
    "分析师报告": "最新的行业分析报告指出，科技公司的创新将成为未来增长的主要推动力。",
}

def build_prompt(examples, sentence):
    class_list = list(examples.keys())
    prompt = (
        f"你是一个金融专家，需要对输入的金融领域文本进行分析，"
        f"将类型归类到{class_list}，对于不在这四类中的数据，输出'不清楚类型'。以下是几个示例分类：\n"
    )
    for ctype, example in examples.items():
        prompt += f'"""{example}是{class_list}里的什么类别？""" """{ctype}。"""\n'
    prompt += f'"""{sentence}是{class_list}里的什么类别？"""'
    return prompt
```

注意提示词里那句"对于不在这四类中的数据，输出'不清楚类型'"——这是**边界约束**。不加这句，模型遇到第四个类别之外的文本时会硬选一个，而不是承认不确定。

## 三、Chain-of-Thought：让模型写出推理过程

CoT 的核心很简单：**要求模型先展示中间推理步骤，再给最终答案**。

它分两种：

**Zero-shot-CoT**：不给示例，只加一句咒语。

```
请一步步思考，然后回答问题。

问题：一个商店卖铅笔，每支 2 元。如果有人有 20 元，他最多能买多少支铅笔？
```

就这么一句"让我们一步步思考"（Let's think step by step），就能触发模型展开推理链。这是提示词工程里性价比最高的一招——零成本，效果显著。

**Few-shot-CoT**：给出带**完整推理过程**的示例，而不只是答案。

```
示例：
问题：一个池塘里有 15 条鱼，钓走了 6 条，又放进去 3 条，现在有几条？
推理：初始有 15 条。钓走 6 条后剩 15 - 6 = 9 条。再放入 3 条，9 + 3 = 12 条。
答案：12 条。

现在请回答：
问题：...
```

示例里必须写出**推导步骤**，只写答案的话，模型会照着跳过推理。

**为什么有效**：大语言模型是逐 token 自回归生成的，每个 token 的预测依赖前面所有 token。让它先写出中间步骤，相当于为最终答案生成了更多正确的前置条件。对多步推理问题（数学应用题、逻辑判断、复杂计算），提升尤其明显。

**代价**：输出变长，token 消耗增加，延迟上升。所以 CoT 不适合简单任务。

## 四、Self-Consistency：多条路径投票

Self-Consistency 解决的是"**推理过程不稳定**"的问题——同一个问题问三次，模型可能走三条不同的推理路径，给出三个不同的答案。

思路是：不只生成一个答案，而是**生成多条不同的推理路径，对最终答案投票**，选出现次数最多的。

### 方案一：单次提示词内自投票

```
你是一个数学老师。请用 3 种不同的方法来推理这个问题，并分别给出最终答案。
最后请总结：哪个答案出现次数最多，把它作为最终的正确答案输出。

问题如下：
一个商店卖铅笔，每支 2 元。如果有 20 元，最多能买多少支铅笔？
```

模型可能输出：

```
直接除法：20 ÷ 2 = 10 支
逐步累加：每次减 2 元，共可减 10 次，剩 0 元 → 10 支
画图法：把 20 元分成 10 个 2 元的段 → 10 支
结果：三种方法都得出 10 支
```

**优点**：实现简单，一次调用搞定，成本低速度快。
**缺点**：三条"不同路径"由同一次生成产生，多样性有限；投票也可能不稳定。

### 方案二：Prompt Chaining + 程序投票

拆成三步，用代码控制：

第一步，让模型生成不同的解题思路（不解题）：

```
请用 3 种不同的方法推理这个问题，只需给出推理思路，不需要解答。
输出格式为：{"思路一": "xxx", "思路二": "xxx", "思路三": "xxx"}

问题：一个商店卖铅笔，每支 2 元。如果有 20 元，最多能买多少支铅笔？
```

第二步，把每个思路分别拼成独立提示词，各自调用一次模型求解。

第三步，在代码里收集结果，程序化投票。

```python
from collections import Counter

def self_consistency_vote(question, approaches, llm_call, n=3):
    """对同一问题用多种思路分别求解，再投票选出最终答案。"""
    answers = []
    for approach in approaches:
        prompt = f"请用如下思路解决这个问题，只输出最终的数字答案。\n思路：{approach}\n问题：{question}"
        answers.append(llm_call(prompt).strip())

    # 投票：取出现次数最多的答案
    counter = Counter(answers)
    best, count = counter.most_common(1)[0]
    return best, count, answers
```

**优点**：多样性真正独立（每次是独立的模型调用），结果更稳健。
**缺点**：调用 N 次，成本和耗时都是 N 倍。

### 什么时候值得用

Self-Consistency 是**用成本换准确率**的手段。适合：

- 高价值的复杂推理（法律条款判断、医疗建议、金融风控）
- 单次错误代价远高于多次调用成本的场合

不适合的场景：简单分类、格式转换、实时对话——这些用它是纯浪费。

## 五、如何选型

不是技术越高级越好。判断标准是**任务复杂度**和**模型能力**的匹配：

| 任务特征 | 推荐技术 | 理由 |
| --- | --- | --- |
| 简单、模型见过很多（情感分类、格式转换） | Zero-shot | 加示例和推理都是浪费 |
| 格式要求严格、需要统一口径 | Few-shot | 示例是锁定格式最有效的手段 |
| 多步推理、数学计算、逻辑判断 | Zero-shot-CoT | 一句"一步步思考"，性价比最高 |
| 推理复杂且模型能力一般 | Few-shot-CoT | 示例既教推理又教格式 |
| 高风险、要求极高准确率 | Self-Consistency | 用成本换稳健 |

两个典型的**用力过猛**案例：

- 从一句话里抽人名，用 ReAct 框架——本来一次调用就够，硬生生搞成多轮循环，效果没提升还多花几倍 token
- 把所有问题都加上"请一步步思考"——简单查询也被迫生成几百字推理过程，用户等得久，账单也涨了

反过来，**该用没用**的典型是：拿弱模型做多步数学推理，不加 CoT，结果幻觉严重。这时候正确的选择是上 CoT 或 Self-Consistency。

## 小结

四种技术对应四个难度档：**Zero-shot（直接问）→ Few-shot（给示例）→ CoT（写推理）→ Self-Consistency（多路径投票）**。往上走，效果提升，成本和延迟也提升。

选型的核心判断是"这个任务对当前模型来说难不难"。简单任务用简单技术，把复杂技术留给真正需要的地方。

还有一点必须记住：**提示词不是一锤子买卖**。再好的初始设计也要经过"编写 → 评估 → 迭代"的循环。这个迭代过程，才是提示词工程真正的主体工作。

当单个提示词已经拆到很细仍然不够用时，就要考虑把任务拆成多个提示词串起来执行——这就是 [Prompt Chaining 与 ReAct：让模型分步骤完成任务](article.html?slug=prompt-chaining-react)。
