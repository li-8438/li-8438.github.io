技术选型里有个很常见的心理：**用 SQLite 像是“还没长大”，用 Postgres 才像是正经项目。** 于是不少个人项目和早期产品在第一天就背上了独立数据库服务的运维成本，而它带来的好处一个都没用上。

这篇文章想说的其实很简单：**SQLite 默认是对的，Postgres 是当你遇到具体信号之后的升级，而不是起点。**

## 一、SQLite 被低估的地方

**零配置本身就是巨大价值。** 不需要起服务、不需要管端口、不需要配用户权限、不需要处理连接串。对个人项目来说，这意味着：

- 本地开发和生产环境完全一致，不存在“我这儿好的”
- 备份就是拷一个文件
- CI 里跑测试不需要额外拉起数据库容器
- 新同事 clone 下来就能跑

**它不是“玩具数据库”。** SQLite 是部署量最大的数据库引擎，跑在每台手机、每台浏览器里。它支持事务、支持外键、支持 JSON 函数、支持窗口函数、支持 CTE。中小型读多写少的场景，它的性能往往比网络往返的 Postgres 更好——因为查询没有网络开销。

**开启 WAL 模式后并发能力足够。** 默认的回滚日志模式下，写会阻塞读。打开 WAL 后变成读写不互相阻塞：

```sql
PRAGMA journal_mode = WAL;      -- 写不阻塞读
PRAGMA synchronous = NORMAL;    -- 平衡持久性与性能
PRAGMA busy_timeout = 5000;     -- 遇到锁等 5 秒而不是立刻报错
```

`busy_timeout` 这一项尤其容易被漏掉：不设的话，并发写入时会立刻抛 `database is locked`，而不是等一会儿。

## 二、该换 Postgres 的四个信号

不要因为“以后可能会需要”而提前迁移。等到下面这些信号真的出现，再动：

**信号一：并发写入成为瓶颈。** SQLite 在任意时刻只允许一个写事务。写 QPS 低的时候没问题，一旦出现多个进程/线程持续写入，锁竞争会让延迟急剧上升。注意是**并发写**，不是数据量——数据量到几十 GB 而写入很少，SQLite 依然跑得很好。

**信号二：要部署多个实例。** 这是最硬的信号。SQLite 的数据库文件绑定在一台机器的文件系统上，一旦服务要横向扩展到多副本，或者要跑在 Serverless 这种无持久本地存储的环境里，就必须换成独立数据库服务。

**信号三：需要更强的约束和类型。** Postgres 有丰富的类型（数组、范围、网络地址、几何）、更强的一致性保证、可延迟约束、部分索引、物化视图。当你发现自己在应用层写一堆校验逻辑来弥补数据库能力的缺失时，就该考虑了。

**信号四：需要特定扩展。** 全文检索（尤其是中文）、向量检索（pgvector）、时序、PostGIS。这些在 SQLite 里要么没有，要么要靠应用层硬凑。

## 三、迁移边界：别把方言写进业务层

决定迁移之后，**成本的高低几乎完全取决于之前的代码组织**。

如果 SQL 散落在业务代码各处，迁移就是一场逐行重写。正确做法是守住一条边界：**业务层只依赖仓储接口，不接触 SQL 方言。**

```python
# 业务层：只依赖抽象，不知道底下是 SQLite 还是 Postgres
class ArticleRepository(Protocol):
    def list_recent(self, limit: int) -> list[Article]: ...
    def search(self, keyword: str) -> list[Article]: ...
```

```python
# 仓储实现：方言只出现在这里
class SqliteArticleRepo:
    def list_recent(self, limit: int):
        return self.db.query("SELECT * FROM articles ORDER BY date DESC LIMIT ?", (limit,))
```

这样迁移时只需要换一个实现类。**这条边界的价值不止于迁移**——它同时也是测试时 mock 数据库的接入点。

## 四、真正咬人的方言差异

下面这些是迁移时实际会报错或产生错误结果的地方，不是理论差异。

| 差异点 | SQLite | PostgreSQL | 后果 |
| --- | --- | --- | --- |
| 参数占位符 | `?` | `%s` 或 `$1` | 全部查询报错 |
| 布尔值 | `0` / `1` | `true` / `false` | 查询结果异常 |
| 自增主键 | `INTEGER PRIMARY KEY` | `SERIAL` / `GENERATED` | 插入失败 |
| 字符串拼接 | `\|\|` | `\|\|` 或 `CONCAT` | 基本一致，但注意 NULL 传播 |
| 分页 | `LIMIT n OFFSET m` | 同样支持，但深分页要改写 | 深分页性能差 |
| JSON | `json_extract()` | `->`、`->>` 操作符 | 查询全部要重写 |
| 时间 | 常存成字符串 | `TIMESTAMPTZ` | 时区处理不一致 |
| `ALTER TABLE` | 能力有限 | 支持完善 | 迁移脚本要拆分 |

**占位符是最先爆炸的一个。** `?` 换成 `%s` 看起来是机械替换，但如果有拼接 SQL 的地方，替换会漏，然后在运行时才炸。

**时间处理是最隐蔽的一个。** SQLite 常常把时间存成字符串，靠约定保证格式；Postgres 用 `TIMESTAMPTZ` 会做时区转换。两边对“同一个时间”的理解可能差 8 小时，而且不报错。

**布尔值是最容易漏测的一个。** SQLite 里 `WHERE is_published = 1` 能跑，迁到 Postgres 后 `1` 不是布尔值，要么报错要么永远查不到数据。

## 五、一个决策流程

新项目开始时这样判断：

1. **默认用 SQLite**，同时把仓储层边界写干净
2. 打开 WAL 和 `busy_timeout`
3. 观察：有没有并发写瓶颈？要不要多实例？缺不缺某个数据库能力？
4. 出现上述任一信号 → 迁移，这时候因为有仓储层，改动是局部的
5. 始终没出现 → 说明 SQLite 一直是对的，省下了整套数据库运维

**关键在第 1 步和第 2 步同时做。** 只选 SQLite 但把 SQL 写得到处都是，等于把成本推到未来一次性付清；提前写干净仓储层，才保留了“以后能平滑迁移”这个选项。

## 六、容易踩的坑

**为了“看起来专业”而过早上 Postgres。** 结果是为不需要的能力付出了运维成本，本地开发还多了一层环境差异。

**没开 WAL 就下结论说 SQLite 并发不行。** 默认配置下的表现不能代表它的真实能力。

**不设 `busy_timeout`。** 并发写入时立刻报 `database is locked`，让人误以为 SQLite 完全不支持并发。

**把 SQL 写进业务层。** 这是唯一一个会让迁移成本失控的错误，其他问题都好补救。

**以为迁移只是改连接串。** 方言差异会集中爆发，尤其是占位符、布尔值和时间。

## 小结

- **SQLite 默认是对的**：零配置、读写快、备份简单，适合个人项目和早期产品
- **开 WAL + busy_timeout**，能解决绝大部分“SQLite 并发不行”的抱怨
- **四个迁移信号**：并发写瓶颈、多实例部署、更强约束与类型、特定扩展
- **迁移成本取决于仓储层边界**，不是取决于数据库本身
- **方言差异集中在**占位符、布尔值、时间、JSON、`ALTER TABLE` 这几处

先把仓储层收干净，再谈选型——这个顺序反了，后面每一步都会很贵。索引层面的优化思路在两个库之间是通用的，见 [MySQL 索引优化](article.html?slug=mysql-index-optimization)。
