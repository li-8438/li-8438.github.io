初学 Git 最容易卡住的地方不是命令记不住，而是**不知道自己在操作什么**。改动到底在哪儿？`git add` 加到了哪儿？`commit` 又写到了哪儿？

搞清楚「三个区域 + 四种状态」，后面所有命令都是在这张图上移动文件而已。

## 一、先说 Git 和 SVN 的本质差异

理解了这个，后面很多设计就都说得通了。

**SVN 存的是差异（delta）。** 它记录每个版本相对上一个版本改了什么：

```text
版本1  新建 fileA.js
版本2  fileA.js 第 38 行新增注释
版本3  fileA.js 第 38 行删除注释
```

想拿到版本 3，得从版本 1 开始，依次把版本 2、版本 3 的差异打上去。

**Git 存的是快照（snapshot）。** 每个版本都是当时项目完整状态的一份快照。想拿版本 3，直接把那份快照拿出来就行。

所以 Git 切版本快，SVN 切版本慢——这是设计上的根本差异。

但这里有个**必须澄清的点**：很多人由此以为 Git 是"每个版本都把文件完整复制一遍"，磁盘会爆炸。其实不是。

Git 在物理存储上做了复用：**文件内容没变的文件，新快照不会重新存一份，只存一个指向原有内容的指针**。真正被复制的只有那些改动过的文件。

```text
版本1:  [fileA 快照①] [fileB 快照①] [fileC 快照①]
版本2:  [fileA 快照②] [fileB  ↗复用①] [fileC ↗复用①]
版本3:  [fileA  ↗复用①] [fileB  ↗复用①] [fileC 快照③]
```

所以准确的说法是：**逻辑上是全量快照，物理上是增量存储**。既拿到了快照的访问速度，又没有付出快照的存储代价。

这个设计带来的直接好处是——**分支几乎零成本**。开一个分支不过是新建一个指向某份快照的指针，不复制任何文件。这是后面所有分支玩法的基础。

## 二、本地操作：断网也能提交

Git 是分布式的，你的本地仓库是**完整的仓库**，不是远程仓库的"工作副本"。

这意味着：

- 断网时照样能 `commit`，改动安全地存在本地
- 有网了再 `push` 同步到服务器
- 断网时也能看完整历史、切分支、回滚

SVN 做不到这点——它的历史在服务器上，断网就基本干不了活。

这个差异在实践中的意义是：**你可以放心地频繁提交**。改到一个说得过去的小节点就 `commit` 一次，不用等到"这个功能做完了"才敢提交。本地提交没有代价，但它给了你无数个可以回退的锚点。

## 三、三个区域

| 区域 | 在哪 | 做什么用 |
| --- | --- | --- |
| 工作区（Working Directory） | 你编辑器里看到的目录 | 实际改文件的地方 |
| 暂存区（Staging Area / Index） | `.git/index` | 挑出"这次要提交哪些改动" |
| 仓库（Repository） | `.git` 目录 | 提交后永久保存的快照 |

工作流程就是三步：

```text
1. 在工作区改文件
2. git add    → 把改动放进暂存区
3. git commit → 把暂存区内容写成一个快照存进仓库
```

**暂存区是 Git 相对 SVN 多出来的一层，也是很多人觉得 Git 别扭的地方。** 为什么要多这一步？

因为它让你能**精确控制每次提交包含什么**。你改了五个文件，但其中两个是调试用的临时改动，那你可以只 `add` 那三个相关的，把它们提交成一个干净的 commit，把调试改动留在工作区。

没有暂存区，你只有两个选择：要么全提交（把调试代码混进去），要么手动把调试代码删掉再提交。

## 四、四种状态

一个文件在任意时刻，一定处于这四种状态之一：

| 状态 | 含义 | `git status -s` 显示 |
| --- | --- | --- |
| 未跟踪（Untracked） | 新建的文件，Git 还没管它 | `??` |
| 未修改（Unmodified） | 工作区和仓库内容一致 | 不显示 |
| 已修改（Modified） | 改了但没进暂存区 | ` M`（红色） |
| 已暂存（Staged） | 改动进了暂存区 | `M `（绿色） |

状态流转是这样的：

```text
新建文件 → 未跟踪(??)
   ↓ git add
已暂存(A)  → git commit → 未修改(干净)
   ↓ 修改文件内容
已修改(M 红色)
   ↓ git add
已暂存(M 绿色) → git commit → 未修改(干净)
```

几个容易看错的地方：

**`M` 在左边还是右边不一样。** `git status -s` 输出两列，左列是暂存区状态，右列是工作区状态。`M `（M 在左）表示已暂存；` M`（M 在右）表示改了但没暂存。

**`git commit -a -m "..."` 可以跳过 `git add`**，直接把工作区的改动提交。但它只对**已被跟踪**的文件有效——新建的文件（未跟踪）还是得先 `git add` 一次。很多人在这里踩坑：新文件没 `add` 过就 `-a`，结果文件根本没进去。

**未修改是 Git 操作的"终点"。** 当你看到 `git status` 输出 "nothing to commit, working tree clean"，就说明工作区、暂存区、仓库三者一致了。

## 五、第一次使用要做的配置

```bash
# 查看当前用户名 / 邮箱
git config --global user.name
git config --global user.email

# 设置（如果没输出就是没设置过）
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"

# 查看所有全局配置
git config --list --global
```

这个配置会写进每一条 commit 记录。**建议一开始就设对**——如果不设，Git 会用机器名加用户名拼一个出来，出来的作者信息会很奇怪，而且事后改历史很麻烦。

顺手设几个能省很多事的配置：

```bash
# 让 git pull 默认用 rebase，避免产生一堆无意义的 merge commit
git config --global pull.rebase true

# 起别名
git config --global alias.st "status -s"
git config --global alias.lg "log --oneline --graph --decorate"

# 任何命令加 -h 都能看帮助
git commit -h
```

## 六、日常最短命令集

如果只记最少的命令，够用一辈子的是这几条：

```bash
git init                      # 初始化仓库（在要管理的项目目录下执行）
git status -s                 # 看状态（最高频的命令，没有之一）
git add 文件名                 # 加单个文件到暂存区
git add .                     # 加所有改动
git commit -m "描述"           # 提交到仓库
git log --oneline             # 看提交历史（一行一条）
git log -3                    # 只看最近 3 条
```

关于 commit 信息，有个值得养成的习惯——**用「操作类型：操作内容」的格式**：

```bash
git commit -m "feat: 新增两个接口（调用模型、结束会话）"
git commit -m "fix: 修复并发下会话状态串号的问题"
git commit -m "docs: 补充部署文档的环境变量说明"
```

这不是形式主义。三个月后你回头查"这个 bug 是什么时候引进来的"，一条 `fix: 修复xxx` 能让你在几十条 "update"、"修改"、"123" 里一眼定位到目标。而且这种格式能被工具自动解析，直接生成 changelog（后面讲 Conventional Commits 会展开）。

## 七、.gitignore：别把垃圾提交进去

有些文件不该进仓库：依赖目录、编译产物、本地配置、密钥文件。建一个 `.gitignore` 文件把它们排除掉：

```bash
# 开头的行是注释
# 依赖
node_modules/
__pycache__/
venv/

# 构建产物
dist/
build/
*.pyc

# 本地环境与密钥（重要！）
.env
.env.local
*.pem

# 编辑器与系统
.vscode/
.DS_Store

# 日志
*.log
```

通配符规则：

| 写法 | 含义 |
| --- | --- |
| `#` 开头 | 注释 |
| `/` 结尾 | 匹配该目录下的所有文件 |
| `*` | 匹配任意个字符（不含路径分隔符） |
| `**` | 匹配任意层目录 |
| `/` 开头 | 只匹配当前目录下的该文件 |
| `!` 开头 | 取反，即"不忽略"这个 |

**最后一行 `.env` 是最容易被忽略的一条。** 把密钥提交进仓库是件很麻烦的事——即使你后面删了，它依然存在于 Git 历史里，任何人 checkout 到那个版本都能拿到。**一旦推到公开仓库，就当作泄露了，正确的做法是立刻去吊销那个密钥，而不是只删文件。**

还有个补救点：如果文件已经被跟踪了，再写进 `.gitignore` 是**不生效的**。得先把它从跟踪列表移除：

```bash
git rm --cached 文件名        # 从仓库移除，但保留本地文件
```

## 八、风险命令：这三个碰之前想三秒

Git 有几条命令会**不可逆地丢弃你的改动**，用之前务必确认：

```bash
git checkout -- 文件名    # 丢弃工作区的改动，回到仓库的版本
git reset --hard 哈希值    # 强制回退到某个版本，丢弃之后的所有改动
git rm -f 文件名          # 从仓库和本地磁盘都删除
```

`git checkout -- 文件名` 是最高频的误操作来源。你改了半天想"撤销一下"，结果这条命令把改动全清了，而且**没有二次确认**。

安全习惯：

1. **不确定就先 `git stash`**，把改动暂存起来，而不是直接 checkout 丢弃
2. **重要改动先 commit 再操作**——提交了的东西基本都能找回，没提交的丢了就是真丢了
3. 真丢了也别慌，`git reflog` 有救（后面讲 Git 救援时会展开）

相对安全的是 `git rm --cached 文件名`——它只把文件从仓库移除，**本地文件会保留**，常用于"误提交了不该提交的文件"这种场景。

## 小结

Git 的心智模型就三句话：

1. **三个区域**：工作区改、暂存区挑、仓库存。所有命令都是在这三者之间搬东西
2. **四种状态**：未跟踪 → 已暂存 → 未修改 → 已修改，形成闭环
3. **快照而非差异**：所以切版本快、开分支便宜，但磁盘占用靠内容复用控制住了

入门之后马上面临的问题是「怎么和别人协作」——分支怎么开、冲突怎么解、代码怎么推到远程，这些见 [Git 分支与远程协作：从开分支到解冲突](article.html?slug=git-branch-remote)。
