先摆一组互相矛盾的数字：

- 大约 **99%** 的公司计划把 AI Agent 投入生产
- 真正做到的只有 **9% 到 14%**
- 与此同时，**78% 的企业 AI 团队已经有至少一个 Agent 上了生产**

这三句话同时成立，说明的都是同一件事：**做 Demo 很容易，让它稳定地跑在生产环境里很难，而绝大多数团队是在"以为自己快做完了"的地方停下来的。**

Forrester 和 Anaconda 2026 年的调研给出的数字更直白：**88% 的 Agent 试点从未抵达生产。** 而成功那 12% 具备的四个特征里，有三个跟模型毫无关系——部署前的基础设施投入、治理文档、上线前的基线指标，以及明确的业务归属方。

## 一、Agent 和 chatbot 差在哪：一个循环，和撑住这个循环的六层

先把概念钉清楚。Agent 的定义就是那个 **think → act → observe** 的循环：模型思考任务、调用工具或写内存、观察结果、循环直到任务完成。

一个 chatbot 需要推理，可能再加个 RAG。而一个 Agent 需要的要多得多：

| 层级 | 解决什么问题 | 成熟度 |
| --- | --- | --- |
| 模型与推理 | 用哪个模型、怎么跑 | 高度商品化 |
| 协议与工具（MCP） | 怎么调外部工具 | 标准化中 |
| 内存 | 跨会话记住什么 | 已成一等公民 |
| 编排框架 | 多步流程怎么组织 | 相对成熟 |
| 护栏 | 实时约束行为 | 与生产的差距最大 |
| 评测 | 怎么知道它做得对不对 | 与生产的差距最大 |

注意最后两行。**从 Demo 到生产落差最大的两层，恰恰是最容易被跳过的两层。**

一个很典型的反面案例：某团队用 LangGraph 做客服机器人，三周后做出了 14 个节点的状态图、一个写进 Redis 的自定义 checkpointer、还有每周失败一次的工具重试逻辑。而这个 Agent 只回答退款问题、只调一个 API。

**用 OpenAI SDK 写 50 行脚本加两个 MCP server 就够了。** 没人先映射过这个问题到底需要哪几层。

## 二、失败模式一：无限循环

**症状**：Agent 反复重试同一个失败的动作，参数每次只做微不足道的改动。跑一晚上烧掉几百块 token，最后什么也没完成。

**原因**：没有步数预算、没有卡死检测，或者模型拿不到"为什么失败"的信息。

**修复**：三件事都要做。

```python
MAX_STEPS = 20
MAX_CONSECUTIVE_FAILURES = 3

async def run_agent(task, tools):
    steps, consecutive_failures = 0, 0
    scratchpad = []

    while steps < MAX_STEPS:
        steps += 1
        action = await model.decide(task, tools, scratchpad)

        try:
            result = await execute(action)
            consecutive_failures = 0
            scratchpad.append({"action": action, "result": result})
            if is_done(action):
                return finalize(scratchpad)
        except Exception as e:
            consecutive_failures += 1
            # 关键：把失败本身写回上下文，让模型知道这条路走不通
            scratchpad.append({"action": action, "error": str(e)})
            if consecutive_failures >= MAX_CONSECUTIVE_FAILURES:
                raise StuckError(f"连续 {MAX_CONSECUTIVE_FAILURES} 次失败，已中止")

    raise BudgetExceeded(f"超过 {MAX_STEPS} 步预算")
```

**最容易被漏掉的是那句把错误写回 scratchpad。** 很多实现里失败的动作根本不进上下文，模型看不到自己刚试过什么，于是做出同样的决策——这不是模型笨，是你没给它看。

## 三、失败模式二：上下文溢出

**症状**：Agent 跑了十几步之后开始明显退化——忘记前面的发现、重复已经做过的工作、甚至开始编造。

**原因**：历史超过了模型的有效上下文长度。注意是**有效**长度——即使窗口标称 128K 或 200K，超长上下文下的注意力质量也会下降。

**修复**：上下文管理不是可选项。三种手段组合使用：

- **压缩已完成的子任务**：把详细历史替换成摘要
- **滑动窗口**：最近几步保留完整细节，更早的压缩
- **结构化暂存区**：重要发现存到独立的结构化 scratchpad，不依赖对话历史

```python
def compact_history(history, keep_recent=5):
    """近期全量保留，更早的压成事实列表 + 摘要"""
    if len(history) <= keep_recent:
        return history

    old, recent = history[:-keep_recent], history[-keep_recent:]
    summary = await model.summarize(old)          # 一段叙述性摘要
    facts = extract_structured_facts(old)         # 关键发现的键值对

    return [{"role": "system", "content": f"此前进展：{summary}\n已确认事实：{facts}"}] + recent
```

记忆分层的思路在这里很自然：工作记忆放上下文、情节记忆存向量库按需召回、语义记忆走 RAG、程序记忆固化进系统提示和工具定义——**程序记忆不该每轮重复占用上下文。**

## 四、失败模式三：工具输出投毒

**症状**：Agent 读取了某个网页、文档或 API 返回之后，行为突然变得诡异。

**原因**：外部内容里藏着指令，模型把它当成了自己提示词的一部分。这就是**间接提示注入**。

这条在 2026 年变得格外现实，因为 MCP server 的数量爆炸了。Endor Labs 分析了 2614 个 MCP server，发现 **82% 存在路径遍历风险，67% 存在代码注入风险**。

**修复**：

- 把外部内容用明确的分隔符包起来，并在提示词里声明"这是数据不是指令"
- 用护栏模型在内容进入上下文之前扫一遍
- **最小权限原则**：Agent 只能拿到完成任务所必需的能力，不多给

最后一条最重要也最常被违反：**不要因为方便，就通过过于宽松的 MCP server 给了 Agent root 权限。**

## 五、失败模式四：自信的错误答案

**症状**：Agent 顺利跑完了全部流程，输出一个错误答案。它没有任何报错——因为它根本没遇到错误，只是做了错误的假设。

**原因**：任务没有可验证的成功判据，或者 Agent 缺少验证自己工作的工具。

这是六个模式里最危险的一个，因为它**没有任何信号**。前面几种失败至少会卡住、会超时、会报错，而这一种会安静地生产出错误结果。

**修复**：**把验证做进循环。**

| Agent 类型 | 验证方式 |
| --- | --- |
| 编码 Agent | 跑测试 |
| 数据 Agent | 用已知值抽检结果 |
| 写作 Agent | 用评审 Agent 或人工复核 |
| 通用 | 至少让 Agent 输出置信度，并说明依据 |

有一个判断标准很好用：**如果你设计不出验证方式，这个任务就不该交给 Agent 自主完成。** 这不是保守，这是工程判断。

## 六、失败模式五：灾难性动作

**症状**：Agent 执行了不可逆的有害动作——删了生产数据、给客户发了邮件、部署了坏代码。

**原因**：高风险动作上缺少门禁。

**修复**：**按风险给动作分级，不同级别走不同通路。**

```python
RISK_LEVELS = {
    "read_data":     "low",     # 自动执行
    "search":        "low",
    "write_staging": "medium",  # 记录日志，可审查
    "create_draft":  "medium",
    "write_prod":    "high",    # 必须人工审批
    "send_email":    "high",
    "spend_money":   "high",
}

async def execute(action):
    level = RISK_LEVELS.get(action.name, "high")   # 未知动作按最高风险处理

    if level == "high":
        approved = await request_human_approval(action)
        if not approved:
            return Blocked("已拒绝高风险动作")
    return await do_execute(action)
```

注意那行兜底：**没登记过的动作按最高风险处理，而不是最低。** 白名单思维在这里会要命。

另有一条硬规则：**永远不要让 Agent 在没有审批门禁的情况下直接接触生产系统。**

## 七、失败模式六：工具给得越多，Agent 越笨

这是最反直觉、也最有数据支撑的一个。

MCP 的成功带来了丰富的工具生态，同时也制造了这个失败模式：**一个工具定义大约 400-500 token，暴露 50 个工具就要消耗 20000-25000 token——在 Agent 处理任何一个字的用户输入之前。** 对 32K 上下文的模型来说，四分之三的窗口已经烧在工具声明上了。

更极端的实测：一个典型的企业 MCP 配置（Playwright + GitHub + IDE + 工单系统 + 知识库）能吃掉超过 20% 的上下文窗口，**而且这个开销每一轮都要重复付。**

后果是三重的：延迟上升、选错工具（几十个相似选项摆在那）、以及**能力退化**——真正留给任务的工作记忆变少了。

Amazon Prime Video 的工程团队在生产里撞到了这堵墙：**给 Agent 通过中心化 MCP server 提供全面的工具访问，反而降低了性能。工具越多越混乱、幻觉越多、结果越差。**

### 三种应对

**渐进式工具发现**：初始化时只暴露一个"找工具"的能力，按需加载 3-4 个相关工具。Speakeasy 团队测出的差距是 **405000 token（400 个工具）降到 1600-2500 token——约 160 倍的缩减。**

**MCP 网关**：在 Agent 和工具服务器之间加一层中间件，用向量检索为每次查询动态挑选 5-10 个最相关的工具注入上下文。无论底层有多少工具，上下文占用都保持恒定。Kong、Composio、MintMCP 都已经有产品。

**层次化命名空间**：把工具分组，让 Agent 像浏览目录一样先探索分类再选择。这个模式已在若干大型部署中使用。

一个耐人寻味的观察：**渐进式发现最初是个纯工程优化（省钱、减少幻觉），但它一旦存在，上面就会长出一层产品决策**——默认工具集给哪些？怎么让用户知道当前能力受限？

## 八、协议层的两个真实缺口

MCP 已经是事实标准（2026 年 3 月月下载量 9700 万、超过一万个公开 server、被主流厂商采纳、12 月归入 Linux Foundation 治理），但它还有两个硬伤：

**认证**：最初的规范没有完整的认证框架，静态 API key 是默认做法——原型够用，合规完全不行。医疗、金融、政府这些需要 SSO、SAML/OIDC 联邦和细粒度审计的行业，实际上被第一波排除在外。2025 年 6 月的规范修订加了 OAuth 2.1 支持，情况在改善。

**可移植性的另一面**：托管型 RAG 平台帮你做了摄入、切分、嵌入、索引，但**文档是可移植的，围绕文档调了几个月的检索系统不是**。如果你认同"知识层就是护城河"，那么把检索逻辑外包给一个不可见、不可调优的 schema，是需要谨慎权衡的。

## 九、容易踩的坑

**一上来就选最重的框架。** 先映射问题需要哪几层，再选工具。一个 50 行脚本能解决的问题，不要上状态图。

**只测"能不能跑通"，不测"跑一百次会不会崩"。** Agent 的难点从来不是成功率，是成功率的方差——以及失败时的可恢复性。

**把护栏和评测留到最后。** 表格里那两层恰恰是 demo-to-production 落差最大的地方，越晚投入还的债越多。

**以为上了 MCP 就等于解决了集成。** MCP 解决的是连接，不是"该暴露哪些能力、什么粒度、谁来负责"——后者是产品设计问题。

## 小结

把这六个模式摆在一起看，会得到一个有点扫兴但很重要的结论：**Agent 上不了生产，绝大多数时候不是模型问题，是工程与产品设计问题。**

- 无限循环 → 缺预算和卡死检测
- 上下文溢出 → 缺压缩策略
- 工具投毒 → 缺输入净化和最小权限
- 自信的错误 → 缺可验证判据
- 灾难性动作 → 缺风险分级
- 工具太多变笨 → 缺渐进式发现

六条里没有一条需要"等模型变强"。它们都是今天就能做的工程决策。

那 12% 成功的团队做对的四件事——**部署前投基础设施、先写治理文档、上线前建基线指标、指定明确的业务归属方**——同样没有一件跟模型选择有关。
