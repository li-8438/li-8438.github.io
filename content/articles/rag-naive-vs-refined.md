2025 年那波"RAG 已死"的论调，逻辑听起来无懈可击：既然上下文窗口已经做到 1M token，能塞进十本小说，为什么还要辛辛苦苦建向量库、调分块、做检索？直接把所有文档丢进去让模型自己找不就行了。

一年过去，数据给出的答案很明确：**RAG 框架的使用量在 2024 到 2026 年间增长了约 400%，目前约 60% 的生产级 LLM 应用在用 RAG，同等工作负载下它比长上下文方案便宜 8 到 82 倍。**

死掉的不是 RAG，是**朴素 RAG**——那个"固定长度切块 + 嵌入 + 向量召回 top-k + 塞进 prompt"的四步流水线。它确实撑不住了，因为它把 RAG 里真正困难的部分全部跳过了。

准确的说法是：**朴素 RAG 已死，精细 RAG 正在繁荣。**

## 一、长上下文没有取代 RAG，只是划清了各自的边界

先解决这个最常被问的问题。两者的关系是互补，不是替代，而且分工已经比较清楚：

| 维度 | 长上下文 | RAG |
| --- | --- | --- |
| 适合的数据规模 | 100 篇文档以内、总量 100K token 以下 | 不限，可扩展到千万级 |
| 数据更新频率 | 静态、一次性 | 动态、频繁更新 |
| 单次查询成本 | 高（每次都付全量 token） | 低（只付召回的几千 token） |
| 适用场景 | 一次性深度分析、小规模静态集 | 知识库问答、客服、企业搜索 |
| 成本对比 | 基准 | 便宜 8 至 82 倍 |

判断规则很简单：**静态小规模一次性分析用长上下文，动态大规模且在意成本与延迟的用 RAG。**

一个容易被忽略的点是"长上下文免费"这个前提站不住。虽然部分模型已经取消了长上下文的溢价定价，但你依然要为每一轮对话重复支付那 100K token 的输入费用。当你每天有一万次查询时，这笔账会变得非常具体。

## 二、决策一：分块不是调参，是在定义"可检索的最小语义单元"

这是最重要、也最容易被低估的一步。分块决定了你的系统**能检索到的最小单位是什么**——如果一条关键信息被切成了两半，或者被淹没在一大段无关文本里，那么再好的 embedding 模型和 reranker 也救不回来。

Weaviate 的报告给过一个量级：**同一语料、同一检索器的条件下，最好和最差的分块策略之间能拉开约 9% 的召回率差距。** 而换模型通常拿不到这个幅度。

### 2026 年被证据动摇的两个默认做法

**第一个：10-20% 的块重叠（chunk overlap）是必需的吗？**

几乎每篇教程都这么写。但 2026 年 1 月一篇系统性的 arXiv 分析发现，在其测试设置下**重叠没有带来可测量的收益，只是增加了索引成本**。结论不是"永远不要重叠"，而是：**把它当成一个可调项，而不是必须遵守的默认值。** 这个提醒的价值在于——一个如此普及的默认做法都可能只是惯性，其他"最佳实践"更值得怀疑。

**第二个：语义分块一定更好吗？**

语义分块要先给每个句子算嵌入再判断边界，Chonkie 的基准显示它比基于 token 的分块**慢约 14 倍**（0.33 MB/s 对 4.82 MB/s）。对大语料来说，这是"几小时"和"几分钟"的差别。更尴尬的是，在部分基准上语义分块端到端反而输给了朴素的递归分块——因为句子级相似度在噪声文本上并不可靠。

### 值得记住的一条启发式规则

Pinecone 提过一个很好用的标准：**如果一个块脱离上下文后，人类读起来依然通顺，那模型通常也能读懂。** 这一条能拦掉绝大多数糟糕的分块——从句子中间断开的、表格被拦腰截断的、列表项丢失了标题的。

### 分块策略怎么选

| 策略 | 原理 | 适用 | 代价 |
| --- | --- | --- | --- |
| 递归字符切分（512 token） | 按段落、句子、词逐级降级切 | 通用默认起点 | 几乎为零 |
| 结构感知切分 | 按标题、表格行、函数边界切 | API 文档、Markdown、代码 | 需要可靠结构 |
| 父子分层（parent-child） | 小块 128-256 用于匹配，返回大块 512-1024 用于生成 | 生产的默认形态 | 中等索引成本 |
| 上下文检索（Contextual Retrieval） | 用 LLM 给每个块加 50-100 token 的背景说明再嵌入 | 高价值文档 | 每块一次 LLM 调用 |
| 延迟分块（Late Chunking） | 先过一遍长上下文编码器，再池化成块向量 | 长文档、指代多的文本 | 廉价，需长上下文嵌入模型 |

几个有据可查的数字：

- **Anthropic 的上下文检索**：单独使用把 top-20 检索失败率从 5.7% 降到 3.7%（降 35%）；与 BM25 结合降到 2.9%（降 49%）；再叠加 reranker 降到 1.9%（**降 67%**）。注意这 67% 是整个流水线的效果，不是单点的功劳。
- **结构感知切分对表格**：在 MAUD 法律数据集上，按行感知的表格分块把 MRR 从 0.3576 提到 0.5945，BM25 的 Recall@1 从 0.366 提到 0.754。递归切分把表格切碎的代价是实打实的。
- **文档级摘要前置**：EMNLP 2025 的一篇论文指出，在监管文件、合同这类高度同构的语料里，来自错误文档的块和正确文档的块几乎无法区分；给每个块加上文档级摘要能显著缓解。有个耐人寻味的细节：**通用的摘要提示词效果超过了法律专家手工调优的提示词。**

一个务实的起点：**递归切分 512 token 起手，用真实 query 测 Recall@K，只有当指标证明需要时才升级到语义、分层或延迟分块。**

## 三、决策二：混合检索已经不是加分项，是标配

纯向量检索有一个结构性弱点：**它对精确标识符几乎无能为力。** 用户搜 `CVE-2024-1234`、`getUserById`、产品型号 `XR-200B`，这些字符串在嵌入空间里彼此高度相似，语义检索分不出高下。而这恰恰是企业知识库里最常见的查询类型。

2026 年生产环境的收敛形态是：

```python
# 稠密 + 稀疏 + RRF 融合，再交给 reranker
results = client.query_points(
    collection_name="docs",
    prefetch=[
        Prefetch(query=dense_vector, using="text-dense", limit=50),   # 语义召回
        Prefetch(query=sparse_vector, using="text-sparse", limit=50), # BM25 召回
    ],
    query=FusionQuery(fusion=Fusion.RRF),  # 倒数排名融合
    limit=50,
)
# 融合后的候选再过一遍 cross-encoder reranker，取 top 5-10
```

效果对比很直观：某个 2026 年的基准里，**混合检索 + rerank 的 Recall@5 是 0.816，而纯稠密检索只有 0.587。** 差距来自两者互补——BM25 和嵌入会以不同的方式失败。

如果你已经在用 PostgreSQL，**pgvector 没有原生 BM25**，你需要自己把向量距离查询和 `tsvector` 全文查询拼起来、再手写一个 RRF 融合。这是完全可行的，很多生产系统就是这么干的，但它是"你要拥有和维护的代码"，不是一个开关。

## 四、决策三：rerank 是单点收益最大的一步

Bi-encoder 把 query 和文档分别编码成向量再算相似度，速度快但丢了交互信息；**cross-encoder 把 query 和候选文档拼在一起过一遍模型，直接打分**，能捕捉到 bi-encoder 看不到的相关性信号。

这就是为什么 2025 到 2026 年生产部署里，**质量提升的主要来源不是换数据库，而是加了 rerank 这一层**。常见的 bge-reranker-v2-m3、Cohere Rerank、Voyage rerank-2 都属于这一类。

一个反直觉但很重要的判断：**加 reranker 通常比换向量数据库更值。** 换库省下的是几毫秒，rerank 提升的是召回质量本身。

还有一层容易被忽略——**顺序也影响效果**。"Lost in the Middle" 的研究表明模型对上下文的注意力呈 U 形分布，开头和结尾最强、中间最弱。所以重排不只是"把相关的挑出来"，还包括"把最关键的放在两端"。

## 五、决策四：新鲜度与版本，比你想的更致命

**一份上个季度就已被取代的文档，比没有文档更糟。** 因为它会让模型给出一个看起来有据可依、实际已经过期的答案——而这类错误不会被任何"检索失败"指标捕捉到。

要处理的是三件事：

- **变更传播**：源系统更新后多久能反映到索引里？CDC 有延迟，而延迟期间 RAG 读到的是旧块。
- **版本标识**：块上必须带生效时间、版本号、来源文档 ID，让生成时能引用、能追溯。
- **冲突处理**：同一问题在新旧两版里答案不同，怎么办？这需要产品层面的决策，不是技术问题。

## 六、决策五：知道什么时候"不检索"

这是最反直觉、也最容易被跳过的一步。**注入不相关的上下文会主动损害输出质量。**

2026 年一篇题为 "Less Context, Better Agents" 的论文发现，对长期工具调用型 agent，**选择性保留上下文比保留完整历史能带来更好的决策质量**，同时大幅降低 token 消耗。核心洞察是：**改善模型表现的是更高的相关性，不是更大的信息量。**

实践上意味着：

- 检索结果要有相关性阈值，低于阈值就宁可不注入
- 有些问题（闲聊、纯计算、 formatting 类）根本不该走检索
- **克制是一个设计决策**，不是缺省行为

## 七、先测再改：你没法优化你没在衡量的东西

RAG 有个出了名的难题：**标准评测把分块质量、检索器质量、生成器质量混在一起。** 一个糟糕的 RAG 分数只能告诉你"有地方坏了"，说不出坏在哪。HiChunk 团队就发现现有基准的 ground-truth 证据太稀疏，无法专门评判分块，于是自己建了 HiCBench。

一个能落地的最小评测流程：

```python
# 1. 从真实日志里抽 50 条 query（不要自己编）
# 2. 人工标注每条 query 对应的正确块
# 3. 分别测：纯向量 / 混合 / 混合+rerank 的 Recall@K
# 4. 分别测不同的分块策略
# 5. 把这套跑进 CI，改任何一环都重跑

def recall_at_k(retrieved_ids, gold_ids, k):
    return len(set(retrieved_ids[:k]) & set(gold_ids)) / max(len(gold_ids), 1)
```

关键在第一步：**必须用真实用户 query，不是团队自己写的样例。** 团队写的 query 天然贴合自己设计的意图分类，真实用户不会按你的分类提问——这个分布差异是 RAG 上线后效果崩塌的头号原因。

## 八、容易踩的坑

**在清洗知识库之前就去采购向量数据库。** 这是最常见的顺序错误。垃圾 chunk 进去，任何数据库都救不回 ROI。先治理内容，再扩容硬件。

**换 embedding 模型要全库重建。** 不同模型的向量空间不可比，混用会导致检索结果毫无意义。统一用一个模型，并给将来的升级预留 re-index 窗口。

**无索引的标量过滤 + 亿级向量 = 秒级延迟。** 租户 ID、时间范围这些过滤字段一定要建索引。

**以为向量不能反推原文。** 向量是可以被反推出原文片段的近似信息的。敏感库必须做静态加密和租户级 ACL 过滤——配置错误导致的跨租户泄露是这个领域最常见的事故类型之一。

**追求"最优"分块而忽略了边际收益。** BBVA 的团队描述过每个用例在分块上迭代 3-4 个月。这不意味着要无限调优，而是意味着**要早点把评测搭起来**，让迭代有方向。

## 小结

RAG 不但没有死，它在 2026 年反而成了区分度的来源——因为**模型对所有人都是一样的，语料不是**。当大家都能调用同样的前沿模型时，能不能在你的私有语料里准确找到那一段话，就成了真正的差异。

如果要从这篇里只带走一件事，我希望是这个顺序：

> **先治理内容质量，再做混合检索，再加 rerank，最后才考虑换数据库。**

绝大多数 RAG 系统的瓶颈不在基础设施层，而在"喂给模型的东西对不对"。把顺序搞反，你会花六个月的运维成本去解决一个本来免费的 pgvector 就能覆盖的问题。
